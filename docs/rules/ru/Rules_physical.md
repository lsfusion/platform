## Правила: исполнение

### Таблицы

Хранение данных в базе описано в [таблицах](../paradigm/Tables.md).

1. Таблицы СЛЕДУЕТ объявлять явно для каждого используемого набора классов ключей, а свойства с этим набором параметров — размещать в них опцией `TABLE`. Полагаться в логике на автоматически созданную таблицу `_auto_...` НЕ СЛЕДУЕТ: ее имя строится из идентификаторов классов свойства, отсортированных по алфавиту, поэтому изменение набора классов переносит данные в другую таблицу, а перестановка тех же классов местами оставляет их в той же.

2. Свойства с одинаковым набором параметров, которые обычно читаются вместе, СЛЕДУЕТ хранить в одной таблице: тогда их чтение не требует соединения таблиц.

3. Опцию `NODEFAULT` СЛЕДУЕТ использовать для таблиц узкого назначения, в которые свойства должны попадать только явно. Таблицу с ключами встроенных классов, без ключей или с ключами классов других модулей ОБЯЗАТЕЛЬНО объявлять с `NODEFAULT`, размещая в ней свои свойства опцией `TABLE`: иначе при следующем запуске в неё могут попасть размещаемые автоматически свойства других модулей с такими классами ключей вместе с их значениями.

4. Опцию `FULL` СЛЕДУЕТ указывать для таблицы, которая содержит все объекты классов своих ключей. Она влияет только на способ выполнения запросов, поэтому для таблицы, которая заполнена не для всех объектов, указывать ее НЕЛЬЗЯ.

5. Политику именования СЛЕДУЕТ выбирать на старте проекта. Короткая политика делает имена в базе читаемыми, но при большом количестве материализованных свойств требует явных имен полей, чтобы имена оставались уникальными.

### Материализации

Сам механизм описан в [материализациях](../paradigm/Materializations.md).

1. Материализовать СЛЕДУЕТ вычисляемые свойства, которые читаются или используются в условиях фильтрации значительно чаще, чем меняются данные, от которых они зависят.

2. Материализовать НЕ СЛЕДУЕТ свойства, у которых значение не `NULL` для бесконечного числа наборов объектов, — такое свойство материализовать нельзя. Типичный случай — свойство с параметром встроенного класса, например датой, не ограниченным условием.

3. Материализация цепочки промежуточных свойств умножает работу при изменении данных: СЛЕДУЕТ материализовать результат, который действительно читается, а не каждый шаг вычисления.

4. Свойство, зависящее от часто меняющихся данных и читаемое редко, материализовать НЕ СЛЕДУЕТ — обновление хранимых значений будет выполняться при каждом изменении.

5. После изменения определения материализованного свойства — в том числе изменения или добавления реализации `+=` материализованного абстрактного свойства — или прямого исправления данных в базе хранимые значения ОБЯЗАТЕЛЬНО пересчитать [оператором `RECALCULATE`](../language/RECALCULATE_operator.md). Перезапуск сервера сам по себе этого не делает для изменённого определения: до пересчёта хранимые значения остаются несогласованными с ним, а изменение данных не обязательно исправляет даже те значения, которых касается (см. [материализации](../paradigm/Materializations.md)).

6. Если [операция с множествами](../paradigm/Set_operations.md) читает свойство, созданное другой такой операцией, и падает с ошибкой `TOO LONG QUERY` или итоговый запрос получает плохой план выполнения, внутреннее свойство СЛЕДУЕТ материализовать (если у него не слишком много значений) либо, когда это возможно, предварительно прочитать в локальное свойство: иначе его определение включается подзапросом в текст внешнего запроса (см. [материализации](../paradigm/Materializations.md)). Опции `HINT` / `NOHINT` такой запрос не разделяют. То же относится к обновлению материализованной группировки, когда определения читаемых ею свойств, в том числе её ключей группировки, делают запрос слишком длинным, — уменьшение пакета не обязательно помогает. Материализует ли платформа промежуточные изменения заранее, зависит от сложности и статистики, поэтому такое обновление может падать при одном состоянии сервера и проходить при другом. Один успешный прогон не гарантирует, что следующий уложится в ограничение длины запроса. Если при предварительном чтении в локальное свойство группировка по-прежнему вычисляется для всех групп, затраты на это вычисление сохраняются. Тогда СЛЕДУЕТ рассмотреть материализацию, а вычисление по одному ключу (`FOR ... NOINLINE`) — проверить там, где подходящий индекс позволяет быстро получить данные каждой группы (см. [правило 1 действий](Rules_changes.md#правила-действий)).

7. Условие, в котором несколько условий `OR` соединены через `AND`, а операнды каждого `OR` — свойства разных связанных объектов (`(a1(i) OR b1(stock(i)) OR c1(group(i))) AND (a2(i) OR b2(stock(i)) OR c2(group(i))) AND ...`), может резко увеличивать время компиляции запроса: при ней перебираются сочетания операндов разных условий `OR`, поэтому добавление ещё одного условия может увеличить время компиляции в несколько раз — при десятке таких условий оно может достигать минут. Задержка возникает, когда скомпилированного запроса нет в кэше, — например, при первом выполнении после запуска сервера (см. [материализации](../paradigm/Materializations.md)). Перенос такого условия без изменений в присваивание локальному свойству (правило 6) ничего не меняет, как и опция `COMPLEX` у свойства с таким условием: компилируется то же условие. Локальное свойство СЛЕДУЕТ заполнять по шагам: сначала присвоить `TRUE` по первому условию `OR`, затем для каждого из остальных сбросить значение там, где оно не выполняется, — `l(Item i) <- TRUE WHERE a1(i) OR b1(stock(i)) OR c1(group(i));`, `l(Item i) <- NULL WHERE l(i) AND NOT (a2(i) OR b2(stock(i)) OR c2(group(i)));` — и использовать `l(i)` вместо исходного условия.

8. Не материализованный [выбор](../paradigm/Selection_CASE_IF_MULTI_OVERRIDE_EXCLUSIVE.md) с большим числом условий — в том числе абстрактное свойство, реализации которого являются такими выборами, — СЛЕДУЕТ использовать в выражении один раз. Оператор над выбором может применяться к каждому его результату, а когда два операнда одного оператора — выборы, могут перебираться сочетания их условий, поэтому время компиляции запроса может расти намного быстрее числа условий — до десятков секунд при двух десятках условий и до минут, когда два условия над одним и тем же выбором соединены через `OR`. Задержка возникает до отправки запроса в базу данных, когда скомпилированного запроса нет в кэше (правило 7), а для именованного свойства с таким выражением может возникать и при полном запуске сервера после изменения модулей, на шаге `Synchronizing properties` в логе `start`. Выбор, переданный свойству, которое несколько раз обращается к своему параметру, используется при каждом таком обращении (`capitalize(STRING s) = IF s THEN upper(left(s, 1)) + substrFrom(s, 2);`, `capitalize(kindName(i))`). Если из-за этого компиляция занимает слишком много времени, а такое свойство принимает значение встроенного класса и может быть записано на SQL для используемых SQL серверов с той же обработкой `NULL`, его СЛЕДУЕТ объявлять свойством [`FORMULA`](../language/FORMULA_operator.md) (`capitalize(STRING s) = FORMULA TEXT PG 'upper(left($1, 1)) || substring($1, 2)';`): выбор остаётся одним операндом, сколько бы раз текст ни использовал параметр. В сессии, изменившей данные, от которых зависит выбор, [оператор изменений](../paradigm/Change_operators_SET_CHANGED_etc.md) над ним использует и текущее, и предыдущее его значение. Если выражение в действии использует выбор несколько раз, причём только его текущее значение, это значение СЛЕДУЕТ сначала прочитать в локальное свойство и применять выражение уже к этому свойству. Материализованный выбор (правило 1) читается из хранимого поля в сессии, не изменившей данные, от которых он зависит. После такого изменения компиляция определения выбора может задержать и его чтение, и обновление хранимых значений.

9. Если запрос фильтрует или сортирует по вычисляемому свойству, сочетающему несколько [операторов выбора](../paradigm/Selection_CASE_IF_MULTI_OVERRIDE_EXCLUSIVE.md) над [группировками](../paradigm/Grouping_GROUP.md), — например, форма отсортирована по колонке такого свойства — и построение этого запроса идёт медленно, хотя само свойство читается быстро, свойство, которое нельзя материализовать (правило 2), СЛЕДУЕТ пометить [опцией `COMPLEX`](../language/Property_options.md): иначе условие по значению свойства, в том числе сравнение, которым отсортированная форма позиционируется на текущем объекте, может разворачиваться по условиям и результатам этих выборов, и построение запроса, а не его выполнение, может занимать минуты.

10. Если действию не материализованное свойство, созданное [группировкой](../paradigm/Grouping_GROUP.md), нужно лишь для части объектов, а условие, которое их отбирает, платформа не считает ограничивающим — диапазон с одной заданной границей, диапазон по числовому свойству или по свойству без индекса, диапазон, границы которого — свойства того же объекта, отсутствие значения свойства, — объекты СЛЕДУЕТ сначала записать в локальное свойство присваиванием с условиями, которые не читают группировку, а свойство читать с условием `WHERE` по этому локальному свойству: иначе группировка может вычисляться для всех объектов, а условие — применяться к её результату (см. [материализации](../paradigm/Materializations.md)). В локальном свойстве СЛЕДУЕТ оставлять только объекты, для которых группировка нужна: платформа ограничивает им подзапрос, когда оценивает это как более дешёвое. Разобранные примеры — в статье `How-to_Heavy_computations`.

### Индексы

Сам механизм описан в [индексах](../paradigm/Indexes.md).

1. Индексы СЛЕДУЕТ создавать для свойств, по которым выполняется фильтрация или поиск в формах и запросах, и НЕ СЛЕДУЕТ создавать «на всякий случай»: каждый индекс обновляется при каждом изменении значений его полей.

2. Индексировать можно только материализованные свойства, поэтому индекс по вычисляемому свойству требует его материализации — и решение о ней принимается по правилам материализации из этой же статьи — свойство материализуют потому, что его читают или используют в фильтрации заметно чаще, чем меняются данные, от которых оно зависит, а не ради индекса.

3. Составной индекс СЛЕДУЕТ создавать, когда фильтрация идет сразу по нескольким полям одной таблицы. Первыми в нём ДОЛЖНЫ идти поля, ограничиваемые равенством, а за ними — поле, ограничиваемое диапазоном: именно на такой форме btree-скан сужается лучше всего.

4. Индекс, дублирующий автоматически создаваемые, создавать НЕ СЛЕДУЕТ: уникальный индекс по всем ключам таблицы и индексы по суффиксам ключей уже существуют.

5. Для полей, по которым выполняется поиск операторами `LIKE` и `MATCH`, СЛЕДУЕТ использовать одноименные типы индексов, а не обычный индекс.

6. Значение свойства без параметров, служащее границей диапазона, НЕ СЛЕДУЕТ объединять с другим значением оператором `MIN` или `MAX`: значение такого свойства может читаться из таблицы в самом запросе, и тогда по условию `date(x) > (MIN p(), d) AND date(x) <= (MAX p(), d)` PostgreSQL не отбирает диапазон по индексу по `date`, а просматривает таблицу целиком. Диапазон между двумя значениями СЛЕДУЕТ записывать двумя ветвями, в каждой из которых поле сравнивается с границами напрямую: `(date(x) > d AND date(x) <= p()) OR (date(x) > p() AND date(x) <= d)`. Хранимое свойство без параметров, которое используется в условиях запросов, СЛЕДУЕТ объявлять с опцией `PREREAD`: его значение читается до выполнения запроса и передаётся в него готовым значением.

### Примеры

Таблица на каждый набор классов ключей, свойство размещено в неё опцией
`TABLE`, материализован читаемый результат — построчный `sum` оставлен
вычисляемым, потому что правило 3 запрещает хранить промежуточный шаг
цепочки. В составном индексе поле, ограниченное равенством, стоит перед
полем, ограниченным диапазоном, как требует правило 3 правил индексов.

```lsf
TABLE order (Order);
TABLE orderDetail (OrderDetail);
TABLE skuStock (Sku, Stock);

date = DATA DATE (Order) TABLE order INDEXED;
sum (OrderDetail d) = quantity(d) * price(d);
sum (Order o) = GROUP SUM sum(OrderDetail d) BY order(d) MATERIALIZED TABLE order;

INDEX customer(Order o), date(o);
```

## Правила: модули

1. Ассистент ОБЯЗАН разбивать код lsFusion на модули
   по доменной логике или функциональной области,
   а не по произвольной технической группировке.

2. Ассистенту СЛЕДУЕТ предпочитать относительно короткие модули.

   Один широкий модуль НЕ ДОЛЖЕН продолжать расти,
   когда логика естественно разделяется
   на более мелкие связные модули.

3. Ассистент ОБЯЗАН применять низкую связанность и высокую связность:
   тесно связанные классы, свойства, действия и формы
   СЛЕДУЕТ держать вместе,
   а межмодульные зависимости СЛЕДУЕТ держать узкими и явными.

4. `NAMESPACE` модуля СЛЕДУЕТ выбирать по общему бизнес-домену,
   а не по полному имени модуля.

5. Когда модуль относится к существующему семейству доменов,
   ассистенту СЛЕДУЕТ переиспользовать пространство имён этого семейства
   для всех его элементов.

   Новое пространство имён СЛЕДУЕТ создавать только
   для действительно нового домена,
   а не для каждого технического подмодуля.

6. Если имя модуля уже совпадает с предполагаемым пространством имён домена,
   опускание `NAMESPACE` допустимо,
   поскольку lsFusion использует имя модуля по умолчанию.

   Иначе ассистенту СЛЕДУЕТ указывать `NAMESPACE` явно.

7. Ассистенту СЛЕДУЕТ использовать `REQUIRE`, `EXTEND`,
   абстрактные свойства / действия
   и расширения форм для связывания модулей
   вместо дублирования логики
   или создания god-модуля.

8. Прежде чем добавлять код в существующий модуль,
   ассистент ОБЯЗАН проверить, относится ли логика
   к домену этого модуля.

   Если нет, ассистенту СЛЕДУЕТ создать
   или расширить более подходящий модуль.

9. Вводя новый модуль,
   ассистент ОБЯЗАН осознанно выбирать зависимости
   и избегать циклических или ненужных зависимостей.

10. Чтобы использовать свойство, действие, класс или форму
    из другого модуля, этот модуль ДОЛЖЕН быть достижим
    из цепочки `REQUIRE` текущего модуля — напрямую
    или транзитивно через другие подключённые модули.

    Если модуль-владелец не входит в транзитивное замыкание
    `REQUIRE`, платформа выдаёт ошибку «Property not found»
    (или аналогичную «not found») при запуске.

    Ассистент ОБЯЗАН добавить модуль-владелец
    (или любой модуль, уже подключающий его)
    в список `REQUIRE` текущего модуля до использования
    его элементов.

11. Сервер поставляется со встроенными системными модулями,
    чьи имена НЕЛЬЗЯ переиспользовать для модулей
    приложения — сервер падает при запуске с ошибкой
    `module '<имя>' has already been added`. Встроенные
    имена:
    System, Utils, UserEvents, Scheduler, Email, Time,
    Reflection, Security, Service, Icon, Authentication,
    SystemEvents, Word, WebSocket, Integration, Profiler,
    SQLUtils, ProcessMonitor, DefaultData, Image, Printer,
    Numerator, Chat, Eval, I18n, Com, Sound, Backup, OpenCV,
    Geo, Historizable, Schedule, Document, QZTray, Excel,
    Hierarchy, RabbitMQ, MasterData, Messenger, Whatsapp,
    Skype, Telegram, Viber, Slack.

    Для типовых доменных имён из этого списка (`MasterData`,
    `Document`, `Schedule`, `Numerator`) ассистенту
    СЛЕДУЕТ добавлять к имени модуля префикс проекта.

## Правила: миграция (migration.script)

1. Переименование свойства или действия, либо его перенос
   в другое пространство имён, меняет каноническое имя элемента.
   Всякий раз, переименовывая или меняя пространство имён
   существующего элемента, ассистент ОБЯЗАН отразить это
   изменение в `migration.script` в той же правке. Иначе
   платформа считает старое и новое имена несвязанными
   элементами — старый удаляется, а новый создаётся пустым.

2. Для первичного (`DATA`) свойства это незаметно разрушительно,
   и ассистент ОБЯЗАН проявлять особую осторожность.
   Переименование / смена пространства имён ДОЛЖНЫ быть записаны
   как изменение `STORED PROPERTY`
   (`старое каноническое имя -> новое каноническое имя`), что
   переименовывает соответствующую колонку в базе данных
   и сохраняет её данные. Простое изменение `PROPERTY` переносит
   только настройки политики безопасности и рефлексии,
   но НЕ сохранённые данные: при следующем старте сервера
   старая колонка переименовывается в `_DELETED_` плюс её прежнее
   имя в базе — а если колонка с таким именем уже есть, просто
   удаляется, — а для нового имени создаётся новая пустая колонка,
   так что все существующие значения свойства теряются.

3. Переименование пользовательского класса или его перенос
   в другое пространство имён ДОЛЖНЫ быть записаны как изменение
   `CLASS`, чтобы сохранить его объекты и их данные. Такое
   переименование класса может также изменить канонические имена
   его `DATA` свойств. Они не отслеживаются автоматически и ДОЛЖНЫ
   быть добавлены как отдельные изменения `STORED PROPERTY`.
