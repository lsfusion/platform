Контейнер [`DESIGN`](../language/DESIGN_statement.md) может отрисовываться компонентом React вместо стандартной раскладки. Компонент получает проекцию состояния формы и сам рисует всё поддерево контейнера.

Это возможность только веб-клиента. Десктоп-клиент десериализует контейнер и отрисовывает его обычное (не React) поддерево, поэтому дизайн остаётся рабочим в обоих клиентах.

### Выбор компонента {#selecting-the-component}

В `DESIGN` атрибуту `custom` контейнера присваивается имя компонента строковым литералом, соответствующим `[A-Z][A-Za-z0-9_$]*` (простой идентификатор, начинающийся с заглавной буквы):

```lsf
FORM orders 'Orders'
    OBJECTS o = Order
    PROPERTIES(o) READONLY number, date, sum
;

DESIGN orders {
    BOX(o) {
        custom = 'OrderBoard';
    }
}
```

Форма значения выбирает отрисовщик: строковый литерал, соответствующий `[A-Z][A-Za-z0-9_$]*`, задаёт компонент React, а пустая строка `''`, строка с HTML-шаблоном или свойство дают классический (не React) пользовательский контейнер, описанный в [How-to: Пользовательские компоненты (объекты)](How-to_Custom_components_objects.md). Здесь объект `o` отрисовывается компонентом React `OrderBoard` вместо стандартной таблицы.

Форме, открываемой окном (`SHOW ... FLOAT`; у `DIALOG` окно — расположение по умолчанию), размер вычисляется по содержимому в момент открытия и дальше не меняется: измеряется первая отрисовка компонента, по первым данным формы, а то, что он рисует позже, - новые строки, данные, пришедшие после открытия, - уже нет. Поэтому контейнеру, содержимое которого растёт после открытия, задают базовый размер: `size = (900, 600)` либо отдельные атрибуты `width` и `height`. Без него окно сохраняет размер первой отрисовки, а нарисованное позже содержимое вытесняет кнопки OK / Закрыть за край окна. Закладке (`WINDOW`) размер задаёт окно форм, поэтому там базовый размер не нужен.

Другой путь — не задавать базовый размер контейнеру React, а сделать динамическим само окно: в `DESIGN` самой формы задать её главному контейнеру `size = (-1, -1)` либо только `height = -1` — тогда ширина измеряется и фиксируется при открытии, а высота остаётся динамической. По каждому динамическому направлению окно следует за содержимым компонента, в том числе отрисованным позже. Это годится для формы, на которой нет таблиц (их высота перестаёт подстраиваться под строки), а высота содержимого умеренная: окно центрируется только при открытии, а его высота не ограничена экраном — окно выше экрана прокручивается целиком.

Базовый размер ограничивает и высоту самого контейнера, где бы форма ни открывалась. Без него высота контейнера — это высота того, что нарисовал компонент, и контейнеры над ним растут вместе с ним, поэтому компонент, нарисовавший больше, чем помещается на форме, растягивает всю форму, а прокручивается она целиком — в закладке её главный контейнер. Базовая высота (`height` либо `size`) отделяет размер контейнера от размера содержимого: контейнер получает её, по коэффициенту расширения (`fill`) расширяется из неё в свободное место формы, а не поместившееся содержимое прокручивается внутри него (`overflowVert` по умолчанию `auto`). Форму она растягивает, только когда сама в неё не помещается, — как базовый размер любого компонента.

### Компонент

`OrderBoard` — именованный экспорт из модуля `.jsx` в каталоге `src/main/web`. Как этот модуль компилируется и регистрируется, описано в [How-to: Пользовательские клиентские JS-модули](How-to_Custom_client_JS_modules.md). Примеры здесь используют JSX. Для проекта [без сборки](How-to_Custom_client_JS_modules.md#without-the-build) поместите тот же компонент в файл `.jsx` — он преобразуется на сервере при отдаче. `import` и `export` там недоступны, поэтому ключевое слово `export` опускается, а компонент работает с предоставляемым платформой `window.React` — либо напишите его через `React.createElement` в обычном `.js`. Любой из этих файлов кладётся в `src/main/resources/web/init` (автозагрузка) или в `src/main/resources/web` с регистрацией через `onWebClientInit`.

Компонент — это обычная функция, получающая `props.data` и `props.controller`:

```jsx
export function OrderBoard(props) {
    const orders = props.data.o.list;
    return <div className="order-board">{orders.length} orders</div>;
}
```

Впервые компонент отрисовывается с первой проекцией своего контейнера, когда пришли первые данные формы, и никогда раньше: `props.data` имеет описанную ниже форму с самой первой отрисовки, поэтому ничего в нём не нужно проверять на ещё не пришедшую проекцию.

`props.data` — проекция формы, своя у каждого контейнера `CUSTOM REACT`: в ней только то, что этот контейнер рисует или размещает, поэтому второй React-контейнер формы получает отдельную проекцию, а вместе с ней и собственный [контроллер](How-to_Custom_view_controller.md).

Представление читает и изменяет только части своего контейнера. Общее у контейнеров — сама форма: её текущие объекты и её сессия, поэтому фильтр или текущий объект, изменённые в одном контейнере, видны в другом так же, как в стандартном клиенте.

Каждое свойство, группа и контейнер, которые несёт проекция, — это объект в `data`: значение читается как `.value`, его атрибуты — как соседние поля, а атрибуты колонки списочного свойства — из `data.<group>.<prop>`. Записи, которые контейнер несёт для свойств и компонентов, — данные дизайна: каждая из них есть с самого начала, а показывает ли её форма сейчас, говорит её поле [`hidden`](#display-options), а не то, есть ли она. `data` содержит группу, когда представление рисует ЧАСТЬ этой группы, и содержит ровно те части, которые рисует. Часть группы проецируется — её данные и члены контроллера, которые её меняют, — в тот React-контейнер, где находится компонент этой части: строки и текущий объект — туда, где грид группы (или её дерево), а каждое панельное свойство — туда, где находится само это СВОЙСТВО, в том числе свойство с `lsf` — туда, где его размещает представление, записью, которая его подписывает (у действия с `lsf` записи нет, и части своей группы оно не приносит). Место компонента находится подъёмом вверх от его контейнера: ответ — контейнер `CUSTOM REACT`, а контейнер с `lsf` подъём обрывает, потому что всё под ним рисует платформа. Собственный `lsf` компонента решает только то, какая запись у него там будет — его содержимое или [запись, которая его называет](#lsf-child), — но никогда не то, где. Представление, которое рисует строки — грид лежит внутри кастомного контейнера, и ни он сам, ни контейнер между ними не помечен `lsf`, так что строки рисует React из `data`, а не платформа, — получает `props.data.<g>` равное `{ list, byKey, keys, options, properties }` для этого SID группового объекта `g`, где `list` — массив строк в порядке отображения, `byKey` сопоставляет строковому ключу строки тот же объект строки, а `keys` — массив этих строковых ключей в том же порядке. Ключи `byKey` — это данные приложения, поэтому он создаётся БЕЗ прототипа: строка с ключом `__proto__` лежит в нём обычной записью, а `byKey.hasOwnProperty` и прочие методы `Object.prototype` вызвать не на чем — читайте через `byKey[k]`, а проверяйте через `k in byKey` или `Object.keys(byKey)`. Там, где представление рисует строки, `list`, `byKey` и `keys` присутствуют все: когда у группы нет строк — панельная группа или группа до прихода её первых строк, — они пусты, поэтому представление читает `props.data.<g>.list` напрямую, без проверки на отсутствующее поле. Грид (или дерево), который форма скрывает через `SHOWIF`, говорит об этом в [своей записи](#display-options), `data['GRID(g)'].hidden` — у дерева это `data['GRID(TREE t)']`, одна на все его группы, — а его строки остаются такими, какими сервер прислал их последний раз, как их хранит и грид самой платформы, — пока грид скрыт, сервер может их не обновлять, — поэтому рисуйте их, только пока грид не скрыт. Там, где не рисует, у узла их нет, как нет и `options`: здесь нет строк, о которых они могли бы говорить, и одним из этих имён может называться панельное свойство группы. Группа, ни одной части которой представление не рисует, отсутствует в `props.data` целиком (`props.data.<g>` — `undefined`): контейнер, просто стоящий рядом с платформенным гридом, не получает ничего, как и тот, который лишь обрамляет его (`MOVE GRID(g) { lsf = TRUE; }` — там строки рисует платформа, поэтому контейнер получает [запись, называющую то, что он размещает](#lsf-child), и никаких строк). Запрос строк у [`<List>`](#rendering-rows), когда их здесь нет, — ошибка в представлении, и он бросает исключение: представление показывает причину на своём месте и в консоли. Панельные свойства группы являются полями узла группы в том контейнере, в котором находится само свойство, по интеграционному SID. Верхний уровень `props.data` — это узел пустой группы (уровень формы): каждое свойство пустой группы является полем `props.data` напрямую, по своему интеграционному SID. Атрибуты колонки списочного свойства тоже являются полем группы, в `data.<g>.<prop>` — по одной записи на колонку, — а его построчное значение и атрибуты ячейки лежат в каждой строке. Действия проецируются так же, как свойства: действие, добавленное на группу, является полем каждой строки (списочное действие) или узла группы (панельное действие) — объектом своих атрибутов, как свойство, — поэтому `controller.<group>.<action>.exec(row)` его выполняет (`.exec()` панельного действия строку не принимает). Поле `value` у него тоже есть, но ничего не несёт. `options` — собственные [опции отображения](#display-options) группы, `properties` называет каждую запись СВОЙСТВА, которую несёт этот узел, показываемую или нет, в порядке формы, — а не всё, что на узле лежит: там есть и то, что определяет сама проекция (`list`, `byKey`, `keys`, `options`), и это известно по имени, а не обнаруживается. Число строк — это `list.length`. Каждая строка содержит:

| Поле | Значение |
| --- | --- |
| `key` | Стабильный публичный идентификатор строки — используется как ключ React |
| `isCurrent` | Является ли строка текущей (выделенной) |
| `<integrationSID>` | Каждое списочное свойство — объект `{ value, ...атрибуты ячейки }` по интеграционному SID этого свойства; значение читается как `.value` |
| `objects` | Непрозрачный дескриптор строки, по которому контроллер адресует строку |
| `background`, `foreground`, `selected` | Собственные [опции отображения](#display-options) строки: её цвета фона и текста и признак выделения |

Поэтому `MOVE` панельного свойства и решает, какой движок его рисует: внутри кастомного контейнера его рисует React по `data`, вне его — платформа, там, где оно теперь стоит, и из `data` оно уходит.

Контейнер `CUSTOM REACT` внутри того, что рисует другой такой контейнер, отклоняется при построении формы: это поддерево внешний компонент рисует из `data`, поэтому внутренний никто бы не построил. Помеченный `lsf` — допустим: это отдельный остров, который рисует его собственный компонент, а внешний размещает его так же, как любой другой [дочерний компонент с `lsf`](#lsf-child).

Свойство, сгруппированное по колонкам (`COLUMNS`), спроецировать нельзя: его значения адресуются ключом «строка и колонка», а всё здесь — строка `list`, запись `byKey`, имя на контроллере — означает одну строку. Поэтому React-контейнер не может нести такое свойство — ни колонкой строк, которые он рисует, ни панельным свойством или свойством пустой группы, стоящим в нём: такая форма отклоняется при построении с указанием свойства. В остальной части формы оно остаётся как есть, а у React-представления просто нет для него имени: [контроллер](How-to_Custom_view_controller.md) несёт то же, что и проекция, поэтому у неспроецированного нет члена, а значит, его нельзя передать и в `properties.change`. То же верно всегда, когда имя не выделяет одно свойство: два свойства спроецированной группы могут делить интеграционное имя, только если их записи попадают в разные контейнеры, и тогда каждое представление имеет в виду то, что несёт его собственный узел. В одном контейнере так нельзя — одна запись и один член не могут означать два свойства. Задайте одному из них явный `EXTID`. Если представлению нужны эти значения, объявите обычное свойство.

Член принимает строку только там, где рисуются строки группы, — это `<group>.change(row)` и член списочного свойства, который живёт там же, — и там он принимает объект строки, её дескриптор `objects` либо строковый **ключ**, который дала ей проекция: ключ ищется в `byKey` этого представления. Член панельного свойства и член пустой группы строку не принимают: они действуют на текущих объектах. Что означает каждый из трёх, сказано в разделе [Идентификация строки](How-to_Custom_view_controller.md#row-identity-contract).

`key`, `isCurrent`, `objects`, `background`, `foreground` и `selected` — зарезервированные имена полей строки. В узле группы резервирование следует за тем, что этот узел несёт: `properties`, `change` и `__member` зарезервированы в каждом из них, а `list`, `byKey`, `keys` и `options` — только в том контейнере, который рисует строки группы. В контейнере, несущем лишь панельное свойство группы, их нет, поэтому свойство с именем `list` там ничем не отклоняется. `__proto__` зарезервировано везде: присваивание по этому имени не добавляет поле, а заменяет прототип объекта. Объекта `meta` нет нигде. Форма, в которой проецируемый интеграционный SID занимает зарезервированное имя или два проецируемых элемента занимают одно имя на одном уровне данных, отклоняется с явной ошибкой при её построении. Задайте ей явный `EXTID` или переименуйте. Свойство, которое такой контейнер рисует или размещает, вообще должно иметь имя - представление достаёт его только по этому имени, и запись, и `<Lsf>`: объявленное с `NOEXTID` отклоняется так же - задайте ему `EXTID`. Пустое имя или имя с точкой тоже отклоняется — составное имя, `o.note`, делится по последней точке, — как и группа из нескольких объектов без собственного имени, `OBJECTS (d = X, t = Y)`, там, где представление несёт её часть: её SID — имена объектов через точку, поэтому назовите её, `OBJECTS pair = (d = X, t = Y)`. Свойство или действие с `lsf` называется так же, как любое другое, и всё это относится и к нему.

Значение свойства (`value`) преобразуется в значение JS в зависимости от класса свойства:

| Класс свойства | Значение в JS |
| --- | --- |
| `BOOLEAN` | `true` / `false` (`false` вместо `NULL`) |
| `TBOOLEAN` | `true` / `false` / `null` |
| числовые классы | число |
| пользовательские классы | число — внутренний идентификатор объекта |
| классы даты и времени | `Date` |
| `JSON` | разобранное значение JSON |
| файловые классы | строка со ссылкой для скачивания |
| изображения | строка с адресом или HTML изображения |
| остальные классы | строка |

Кроме `BOOLEAN`, значение `NULL` преобразуется в `null`.

`list` содержит не все строки группы, а только считанную страницу. Вид представления группы, отрисовываемой контейнером React, остаётся таблицей, и группа читается постранично, но, поскольку сама таблица не отображается, размер страницы не подбирается под видимые строки — действует серверный размер страницы по умолчанию (50 объектов). Представлению, которое показывает все строки группы — календарю, доске, карте, — задайте в блоке [`OBJECTS`](../language/Object_blocks.md) опцию `PAGESIZE 0` (читать все объекты) либо явный размер страницы.

Представление, раскладывающее строки в их собственном порядке — поток карточек, лента, — может вместо этого сохранить страницу и вести её за прокруткой, как это делает стандартная таблица. `useSeekOnScroll(controller.<группа>)` возвращает функцию, которой помечается элемент каждой строки. Хук следит, какие из них видны на экране при прокрутке собственного блока представления — ближайшего элемента, прокручивающего строки, который ищется от строки вверх до элемента, в котором нарисовано представление, и не дальше, — и следует правилам самой таблицы: пока текущая запись на экране, прокрутка ничего не меняет; когда она выходит за экран — пересаживается на видимую кромку, через которую вышла, что и запрашивает следующую страницу; при смене страницы пересаженная строка сохраняет свою позицию на экране, так что под взглядом ничего не прыгает; текущая запись, изменённая извне — кликом или программным переходом, — наоборот, докручивается в видимость. Пакт держится на том же контракте, на котором живёт сама таблица, и он на стороне разработчика: страница должна вмещать больше строк, чем видно на экране, — задайте соответствующий `PAGESIZE` в блоке [`OBJECTS`](../language/Object_blocks.md). Тогда окно всегда простирается на страницу дальше текущей записи, и она выходит за экран — и пересаживается, подтягивая следующую страницу, — раньше, чем прокрутке станет некуда двигаться у края загруженного:

```jsx
const seekRef = useSeekOnScroll(controller.o, { enabled: follow });
...
{rows.map(row => <div key={row.key} ref={seekRef(row)}>...</div>)}
```

Опции: `enabled` (по умолчанию `true`) приостанавливает слежение, `threshold` (`0.6`) — какая часть элемента должна быть видна, чтобы считаться на экране, `settle` (`250` мс) — сколько набор строк на экране должен оставаться прежним, прежде чем представление перейдёт, — отсчёт начинается заново, когда строка появляется на экране или уходит с него, а не при каждом событии прокрутки, `onSeek(row)` вызывается при каждом переходе. Используйте один `useSeekOnScroll` на прокручиваемый элемент. Строки, считанные для новой позиции, заменяют `list`, и всё построенное из него — значения и [размещённые представления lsFusion](#lsf-child) — следует за ними.

Хук меняет позицию прокрутки этого блока и отключает в нём собственную привязку прокрутки браузера, поэтому не трогает ничего вне элемента, в котором нарисовано представление: всё, что там, — платформенный контейнер, блок, общий с другим представлением, страница, блок портала — принадлежит чему-то другому. Если строки прокручиваются только в таком элементе, хук не делает ничего — не переходит и не прокручивает к текущей строке, ушедшей из виду, — и один раз сообщает об этом в консоли. Дайте строкам собственный прокручиваемый блок представления — ограниченную высоту и `overflow: auto`.

Число прочитанных строк — `list.length`, а не число строк, пропущенных фильтрами группы, поэтому при постраничном чтении по одной проекции «6 из 23» не показать. Итог — отдельное свойство, которое считает строки в текущем отборе формы [оператором `FILTER`](../paradigm/Filter_FILTER.md), как в [How-to: Состояние таблиц](How-to_Table_status.md), и размещено внутри контейнера, чтобы попасть в `data`:

```lsf
filteredCount 'Orders' = GROUP SUM 1 IF [ FILTER orders.o](Order o);

EXTEND FORM orders PROPERTIES() filteredCount;
DESIGN orders { BOX(o) { MOVE PROPERTY(filteredCount()); } }
```

```jsx
const { o, filteredCount } = props.data;
<div>{o.list.length} из {filteredCount.value ?? 0}</div>
```

Если вместо этого нарисовать свойство для группы (`PROPERTIES() filteredCount DRAW o PANEL`), `MOVE` не нужен: его место по умолчанию — в `PANEL(o)`, внутри `BOX(o)`. Оно становится членом узла группы и читается как `data.o.filteredCount.value`.

```jsx
function Row(props) {
    const r = props.row;
    return (
        <div className={r.isCurrent ? "order order-current" : "order"}>
            <span>{r.number.value}</span>
            <span>{r.sum.value}</span>
        </div>
    );
}
```

### Чтение проекции {#reading}

Компонент читает проекцию одним из двух способов, и выбор — про то, кто перерисовывается при изменении данных.

`props.data` — снапшот целиком. Компонент перерисовывается — со свежим `data` — при любом изменении своей области и рисует всё, что рисует, из нового снапшота. Для небольшого представления это вся история: никаких хуков, чистая функция от данных — примеры выше написаны именно так. Так же читается и вся область целиком — перечисляются её верхние записи, читаются контейнеры. `useData()` без селектора возвращает тот же снапшот.

`useData(selector)` подписывает компонент на срез: он перерисовывается, только когда меняется ссылка `selector(data)`, — поэтому селектор должен возвращать то, что в проекции уже есть (узел группы, строку, запись, значение), и никогда не собирать внутри себя новый объект или массив: такой результат отличается при каждом чтении и приводит к бесконечной перерисовке. Благодаря структурному переиспользованию — не изменившийся узел, строка или запись сохраняют прежнюю ссылку — именно это позволяет компоненту платить только за то, что он читает: компонент, подписанный на узел группы (`useData(s => s.o)`), не замечает остальную область, компонент строки, подписанный на свою строку (`useData(s => s.o.byKey[rowKey])`), — остальные строки. Корень — исключение: платформа передаёт ему новый `props.data` при каждом изменении, поэтому он перерисовывается, на что бы ни был подписан, а то, что он рисует ниже, пропускает перерисовку, только если оно мемоизировано (`React.memo`) и не получает `data`. `useController()` возвращает тот же `controller`, который корень получает параметром, — его идентичность не меняется за жизнь корня, поэтому он безопасен в зависимостях и замыканиях, и передавать его вниз параметром так же правильно.

`useData` и `useController` читают тот корень, внутри которого находится компонент, и о формах ничего не знают. `Lsf` и `useLsf` помещают то, что платформа рисует сама, поэтому одинаково служат и контейнеру формы, и [окну навигатора](#navigator-window). А построенное на групповой и строчной форме проекции — `List`, `BucketScope`, `useBucket`, `Buckets`, `useSeekOnScroll` — существует только для форм: оно обращается к `data.<группа>.list` / `.byKey` / `.keys`, чего нет ни у корня другого вида, ни у представления формы, которое строк этой группы не рисует.

Эти два способа складываются в ступени, и каждая следующая нужна лишь тогда, когда перерисовка предыдущей становится ценой:

1. небольшое представление — `props.data`, рисуется всё;
2. список подлиннее — `props.data` плюс компоненты строк, мемоизированные на уровне модуля (`React.memo` отсекает по стабильным ссылкам не изменившихся строк), или [`List`](#rendering-rows), который делает ровно это;
3. большая доска — подписки вниз по дереву: корень рисует мемоизированные колонки и не передаёт им `data`, колонка подписана на свою [ячейку](#bucketing), строка — на себя, и одно изменённое значение перерисовывает корень и одну карточку.

### Опции отображения {#display-options}

Для каждого свойства, добавленного на форму, платформа вычисляет смысловые опции отображения: заголовок, изображение, цвет фона и цвет текста, состояние «только чтение» или «отключено», комментарий, текст в пустой ячейке, всплывающую подсказку. Они берутся из дизайна свойства и из зависящих от данных опций [блока свойств и действий](../language/Properties_and_actions_block.md) (`HEADER`, `IMAGE`, `BACKGROUND`, `FOREGROUND`, `READONLYIF`, `OPTIONS` и остальных), поэтому опция, зависящая от данных, вычисляется заново для каждой строки. Классы элементов и шрифты стандартного клиента не проецируются: компонент React сам определяет свои CSS-стили. `background` и `foreground` проецируются — это выделение из `BACKGROUND` / `FOREGROUND`, зависящий от данных бизнес-сигнал, а не тема, которой должны владеть собственные CSS-стили компонента. Для свойства, которое контейнер React отрисовывает сам, смысловой результат проецируется в `data` соседними полями рядом со значением свойства, поэтому представлению не нужно вычислять его заново.

Проекция следует тому, что описывает опция, — колонку целиком, одну ячейку или строку:

| Где | Что содержит |
| --- | --- |
| `data.<g>.<integrationSID>` | Для свойства, показываемого в таблице, — атрибуты его колонки, по одной записи на всю колонку: `caption`, `image`, `footer`, `comment`, `tooltip`, `defaultValue` и `hidden`, пока форма его скрывает. Для панельного свойства группы — `value` свойства и его атрибуты, вычисленные для текущего объекта, и `hidden`, пока форма его скрывает; пока текущего объекта у группы нет, `value` пустое, а запись остаётся, как и в панели самой платформы. Для свойства с `lsf` — [запись, которая его подписывает](#lsf-child), без `value` |
| `data.<g>.list[i].<integrationSID>` | Одна ячейка свойства таблицы — её `value` для этой строки и атрибуты ячейки, вычисленные для этой строки: `readOnly`, `disabled`, `background`, `foreground` и остальные |
| `data.<g>.list[i]` | Собственные опции строки, прямо на строке: `background`, `foreground`, `selected` |
| `data.<g>` | `options` — пользовательские опции группы, там, где представление рисует её строки; `properties` — записи СВОЙСТВ, которые несёт этот узел, показываемые или нет |
| `data.<integrationSID>` | Свойство пустой группы — его `value`, атрибуты и `hidden`, пока форма его скрывает; свойство с `lsf` — запись, которая его подписывает, без `value` |
| `data.<componentSID>` | Запись любого другого компонента, который это представление рисует или размещает, — контейнера, объявленного через `NEW` или сгенерированного, как `PANEL(o)` или `TOOLBAR(o)`; грида, как `GRID(o)`, или дерева, как `GRID(TREE t)`; панели инструментов, как `TOOLBARSYSTEM(o)`; и любого компонента с `lsf`, кроме свойства: его `caption` и `image`, если они у него есть, и `hidden`, пока форма его скрывает, по идентификатору компонента дизайна — всегда на верхнем уровне, во что бы компонент ни был вложен. Запись есть всегда; у показанного компонента без заголовка и изображения она пуста |

Каждый атрибут присылается в одном месте, уже вычисленным: статическое значение из дизайна свойства и его построчный результат `BACKGROUND` / `READONLYIF` / … сводятся в одно действующее значение до того, как его увидит представление, поэтому представление читает атрибут прямо оттуда, где он лежит, и никогда не объединяет запись колонки с записью строки. Атрибуты списочного свойства на всю колонку — `caption`, `image`, `footer`, `comment`, `tooltip`, `defaultValue` — находятся в узле его колонки `data.<g>.<prop>`, а его построчное значение и атрибуты ячейки, которые могут меняться по строкам, — в ячейке `data.<g>.list[i].<prop>`:

```jsx
const caption = props.data.o.sum.caption;   // атрибут колонки, один на всю колонку
const cell = row.sum;                        // { value, background, readOnly, ... } для этой строки
```

Динамический `IMAGE` свойства сервер вычисляет один раз для ключа колонки с использованием текущего объекта, а динамический `IMAGE` действия — для каждой строки. Проекция сохраняет это различие: изображение свойства находится в узле его колонки `data.<g>.<prop>`, а изображение действия — в ячейке его строки `data.<g>.list[i].<action>`.

Опция, для которой платформа ничего не вычислила, отсутствует: у свойства без `BACKGROUND` нет `background` в записи его ячейки, а у строки, для которой не вычислено ни одной опции строки, нет `background`, `foreground` и `selected`.

`SHOWIF` управляет самим свойством, и меняет он поле `hidden` записи, а не то, есть ли запись. Когда он скрывает колонку таблицы, запись колонки говорит `hidden: true`, а ячейки колонки остаются в строках без `value`. Когда он скрывает панельное свойство или свойство пустой группы, его запись говорит `hidden: true` и не имеет `value`. Свойство, которое форма скрывает при открытии, остаётся `hidden`, пока не будет прислано впервые. Если нужно отличить скрытое свойство от свойства со значением `value`, равным `null`, читайте `hidden`. У записи, которую форма показывает, поля `hidden` нет вовсе — как нет и любой опции, для которой платформа ничего не вычислила.

| Опция | Что это | Значение в JS |
| --- | --- | --- |
| `type` | Вид, которым было преобразовано значение, — `number`, `boolean`, `string`, `date` либо `json` (разобранный, поэтому значением будет то, что лежало в JSON). Он описывает свойство, а не одно из его значений, поэтому лежит вместе с атрибутами колонки: `data.<g>.<prop>.type` для свойства таблицы и в самой записи для панельного свойства или свойства пустой группы. В ячейке его нет | строка |
| `hidden` | Скрывает ли форма свойство сейчас — его `SHOWIF` или `SHOWIF` контейнера выше. Лежит в записи свойства — в записи колонки для свойства таблицы, в самой записи для панельного свойства или свойства пустой группы — и никогда в ячейке | `true`; нет, пока форма его показывает |
| `caption` | Заголовок свойства | строка |
| `image` | Изображение свойства | строка с HTML изображения |
| `footer` | Значение подвала колонки | преобразуется как значение ячейки |
| `readOnly` | Ячейка доступна только для чтения — по значению, пришедшему из `READONLYIF`. В остальных случаях отсутствует: статически `READONLY` свойство сюда не проецируется, так как представление его и не редактирует | `true` / отсутствует |
| `disabled` | Ячейка отключена — по значению, пришедшему из `DISABLEIF`. В остальных случаях отсутствует. В одной ячейке `readOnly` и `disabled` никогда не приходят вместе | `true` / отсутствует |
| `background`, `foreground` | Цвет фона и цвет текста ячейки | строка с цветом |
| `comment` | Комментарий, показываемый рядом со значением | строка |
| `placeholder` | Текст, показываемый в пустой ячейке | строка |
| `pattern` | Шаблон, по которому отображается значение | строка |
| `regexp`, `regexpMessage` | Регулярное выражение, которому должно соответствовать вводимое значение, и сообщение при несоответствии | строка |
| `tooltip`, `valueTooltip` | Всплывающие подсказки свойства и его значения | строка |
| `options` | Пользовательские опции свойства | разобранное значение JSON |
| `defaultValue` | Значение, с которого начинается редактирование | строка |

Из них `caption`, `image`, `footer`, `comment`, `tooltip` и `defaultValue` — собственные атрибуты колонки, в узле колонки `data.<g>.<prop>` (по одной на колонку). Остальные (`background`, `foreground`, `readOnly`, `disabled`, `placeholder`, `pattern`, `regexp`, `regexpMessage`, `valueTooltip`, `options`) — атрибуты ячейки, в ячейке каждой строки `data.<g>.list[i].<prop>` рядом с её `value`. Сама строка содержит `background` и `foreground` — цвета строки целиком — и `selected`, равное `true`, когда строка выделена, — прямо на строке, а не внутри какой-либо записи свойства.

```jsx
function Row(props) {
    const r = props.row;
    const sum = r.sum;              // { value, readOnly, disabled, background, foreground, ... }
    return (
        <div className="order" style={{ background: r.background }}>
            <span>{r.number.value}</span>
            <input value={sum.value} readOnly={!!sum.readOnly} disabled={!!sum.disabled}
                   style={{ background: sum.background, color: sum.foreground }} />
        </div>
    );
}
```

### Отрисовка строк {#rendering-rows}

Для отрисовки строк группы с экономией перерисовки по строкам используется `window.lsfusion.List`. Это глобальная переменная времени выполнения, поэтому, чтобы записать её как JSX-тег, сначала привяжите её к локальному имени с заглавной буквы. Без псевдонима вызывайте через `React.createElement`. Привязка выполняется там же, где выполняется модуль, а для собранного модуля и для ресурса `.jsx` это происходит до какой-либо отрисовки, поэтому её можно писать в начале модуля. В ресурсе, написанном сразу как `.js`, который отдаётся как есть, компоненты и хуки платформы читаются внутри компонента: модуль выполняется раньше, чем монтируется первое представление, а устанавливаются они при этом монтировании:

```jsx
const List = window.lsfusion.List;
// ...
<List group="o" component={Row} />
// либо, без псевдонима:
React.createElement(window.lsfusion.List, { group: 'o', component: Row })
```

`group` — SID группы объектов. `List` читает строки группы из собственной проекции представления по этому имени, так же как это делает [`BucketScope`](#bucketing), поэтому ему передаётся имя, а не узел. `keys` отрисовывает только часть строк, в заданном порядке, — любой массив ключей строк группы, например отфильтрованную или пересортированную копию `props.data.o.keys`:

```jsx
<List group="o" keys={props.data.o.keys.filter(k => props.data.o.byKey[k].sum.value > 0)} component={Row} />
```

Ключ, которого в группе нет, не отрисовывает ничего. `List`, получивший группу, строки которой это представление не рисует, — такую, от которой у представления есть лишь панельное свойство или нет ничего вовсе, — бросает исключение: рисует ли представление строки группы, задаёт дизайн формы, а не её данные, поэтому это ошибка в представлении, и представление показывает причину на своём месте и в консоли. `List` рисует те строки, которые есть в проекции, а грид, который форма скрывает через `SHOWIF`, свои строки сохраняет, как и грид самой платформы: если у грида есть `SHOWIF`, рисуйте `List`, только пока `props.data['GRID(o)'].hidden` не установлен.

Отрисовывайте `List` как компонент — через JSX или `React.createElement`, — а не вызывая его как обычную функцию: каждая строка отрисовывается компонентом, использующим хуки, поэтому он работает только когда его монтирует React.

`List` задаёт каждой строке ключ `row.key`, передаёт строку в компонент как `props.row` — вместе с `rowKey`, `index` и любыми другими свойствами, переданными в `List`, кроме его собственных `group`, `keys` и `component` — или `children`, который задаёт компонент строки, когда `component` не задан, — и отрисовывает каждую строку через мемоизированную обёртку, привязанную к этой строке, поэтому при изменении перерисовываются только реально изменившиеся строки. Простая альтернатива отображает список напрямую:

```jsx
props.data.o.list.map(r => <Row key={r.key} row={r} />)
```

Зачем нужна экономия перерисовки по строкам. При изменении любой одной строки `props.data.<g>.list` пересоздаётся как новая ссылка на массив, но проекция сохраняет прежнюю ссылку на объект для каждой не изменившейся строки (структурное разделение) — новый объект строки получают только строки, содержимое которых изменилось. Простой `list.map(r => <Row row={r}/>)` пересоздаёт элемент `Row` для каждой записи при изменении любой одной строки, поэтому React перерисовывает их все. Ключ React `key` этого не меняет: он позволяет React сохранять идентичность элемента строки, её DOM и состояние компонента между перерисовками, но не отменяет саму перерисовку. Компилятор React тоже не помогает — он мемоизирует `.map` как одну реактивную область по ссылке на массив, которая только что изменилась, и не оборачивает дочерние строки в `React.memo`, поэтому все строки всё равно перерисовываются.

`window.lsfusion.List` добавляет недостающую отмену перерисовки по строкам: каждая строка отрисовывается через стабильную мемоизированную обёртку, которая следит за этой одной строкой, поэтому изменение значения перерисовывает только изменившуюся строку. Сам список не обходится заново при изменении значения строки — только при добавлении, удалении или перестановке строк, — поэтому обновление рисует только изменившееся. С числом строк растёт лишь проверка своей подписки каждой смонтированной строкой — поиск по её ключу. Чтобы получить отмену перерисовки по строкам вручную без `window.lsfusion.List`, объявите мемоизированный компонент строки один раз на уровне модуля и задавайте ключ `row.key`:

```jsx
const MRow = React.memo(Row);
// ...
props.data.o.list.map(r => <MRow key={r.key} row={r} />)
```

`React.memo(Row)`, создаваемый внутри компонента при каждой перерисовке, каждый раз является новым типом компонента, что сводит мемоизацию на нет и перерисовывает все строки.

### Раскладка строк по ячейкам {#bucketing}

Когда представление раскладывает строки группы не списком, а матрицей — календарь, канбан-доска, расписание, схема рассадки, — каждая строка попадает в производную ячейку (день × сотрудник, колонка статуса и т. п.). `window.lsfusion.BucketScope` поддерживает индекс ячейка → строки по одной группе, и каждая ячейка подписывается только на свой состав:

```jsx
const { BucketScope, useBucket, useData } = window.lsfusion;

const Shift = React.memo(({ rowKey }) => {
    const s = useData(d => d.ss.byKey[rowKey]);          // подписка на свою строку
    return s ? <button>{s.intervalS.value}</button> : null;
});

const Cell = React.memo(({ ck }) => {
    const rowKeys = useBucket(ck);                       // подписка на свою ячейку
    return <div className="cell">{rowKeys.map(k => <Shift key={k} rowKey={k} />)}</div>;
});

export function Board(props) {
    // обеими осями владеет представление: дни показанной недели и одна строка доски на сотрудника
    const days = weekOf(props.data.dates.scheduleFrom.value);
    const rows = props.data.boardEmployees.value;        // например, предразобранное JSON-свойство: [{ id, ... }]
    return (
        <BucketScope group="ss" bucketDeps={[]}
                     bucketOf={s => dateKey(s.date.value) + '|' + (s.assignedTo.value ?? '0')}>
            <div className="grid">
                {rows.map(row => days.map(d =>
                    <Cell key={row.id + '/' + dateKey(d)} ck={dateKey(d) + '|' + row.id} />))}
            </div>
        </BucketScope>
    );
}
```

`<BucketScope group bucketOf bucketDeps>` оборачивает разметку сетки. `group` — SID группы объектов. Группа, строки которой это представление не рисует, приводит к исключению — так же, как в [`List`](#rendering-rows). `bucketOf(row, rowKey)` вычисляет ключ ячейки строки из значений её свойств — строку (любое значение приводится к строке), массив ключей, чтобы поместить строку в несколько ячеек, или `null`, чтобы никуда не помещать. `bucketDeps` перечисляет внешние значения, которые захватывает `bucketOf`, — как массив зависимостей хука, индекс перестраивается при их изменении. Длина массива должна оставаться постоянной.

`useBucket(cellKey)` возвращает массив ключей строк, находящихся сейчас в этой ячейке, в порядке отображения группы, и подписывает компонент только на эту ячейку. Вызывайте его один раз в компоненте ячейки, с её фиксированным ключом (обычные правила хуков). Пустая ячейка всегда возвращает один и тот же замороженный пустой массив. Компонент ячейки превращает каждый ключ строки в компонент строки, который подписывается на свою строку через `useData(d => d.<g>.byKey[rowKey])`, как выше.

Раскладка остаётся за представлением: оно задаёт ключи ячеек — поэтому пустые ячейки существуют и отрисовываются, например как цели перетаскивания, — и разметку ячейки. За платформой — индекс и экономия перерисовки: перемещение строки между ячейками перерисовывает только старую и новую ячейку; изменение значения, не меняющее ячейку строки, перерисовывает только компонент самой строки; все остальные ячейки сохраняют прежнюю ссылку на массив, и их `React.memo` пропускает перерисовку. Простая альтернатива — самостоятельно группировать `data.<g>.list` по ячейкам на каждом рендере — каждый раз пересоздаёт массив каждой ячейки, поэтому любое изменение перерисовывает всю доску.

Когда ячейки образуют плоский список и вся разметка ячейки живёт в одном компоненте, форма `<Buckets group cells bucketOf component/>` выполняет отображение сама, как `List` для строк: по одной мемоизированной обёртке на каждый ключ из `cells`, а компонент ячейки получает `cellKey`, `rowKeys`, `index` и транзитные props. Явную разметку `<BucketScope>` + `useBucket` оставляйте, когда сетку размечает само представление — двумерная матрица, заголовки осей, закреплённые колонки:

```jsx
const { Buckets } = window.lsfusion;
const STATUSES = ['new', 'inProgress', 'done'];

// Card подписывается на свою строку, как Shift выше
const Column = ({ cellKey, rowKeys }) => (
    <div className="column">{rowKeys.map(k => <Card key={k} rowKey={k} />)}</div>
);

<Buckets group="t" cells={STATUSES} bucketOf={t => t.status.value} component={Column} />
```

Используйте раскладку по ячейкам, чтобы помещать строки одной группы в производные ячейки, когда важен только состав, — сводные таблицы, календари, канбан-доски, расписания, сетки с перетаскиванием. Она не вычисляет агрегаты по ячейкам: `useBucket` возвращает ключи строк, а не суммы или количества, и компонент ячейки перерисовывается, только когда меняется массив ключей строк этой ячейки, — живые агрегаты даёт [вид представления *сводная таблица*](../paradigm/Interactive_view.md#property). Для обычного списка строк один к одному используйте `List`. Группировка работает только по собственным спроецированным значениям группы.

### Возврат к lsFusion

`custom` — переход от платформы к React; `lsf = TRUE` — переход обратно. По умолчанию компонент рисует всё поддерево контейнера по `props.data`. Дочерний компонент может вместо этого сохранить своё представление lsFusion: на нём задаётся `lsf = TRUE`, и компонент не рисует его, а размещает через `<Lsf name/>`.

```lsf
FORM orders 'Orders'
    OBJECTS o = Order
    PROPERTIES(o) READONLY number, date, sum
    PROPERTIES() comment = orderComment      // ниже помечено `lsf`; его запись — data.comment
;

DESIGN orders {
    NEW board {
        custom = 'Board';
        MOVE BOX(o) { lsf = TRUE; }        // штатная таблица, размещаемая компонентом
        MOVE PROPERTY(comment) { lsf = TRUE; }
    }
}
```

Дочерний компонент с `lsf` не попадает в `props.data` — платформа строит его представление, передаёт в него значения свойств и отрисовывает его так же, как в обычном контейнере. Компонент определяет только его место. Исключение — его заголовок и изображение, а у свойства ещё и комментарий: они попадают в компонент в `data`, а не в собственное представление дочернего компонента. Свойство с `lsf` проецирует только `{ caption, image, comment, hidden }` — у него нет `.value`, так как значение платформа рисует вместе с остальным оформлением дочернего компонента. Эта запись есть и тогда, когда у него нет ни заголовка, ни изображения, ни комментария: тогда, пока форма его показывает, она пуста. Действие с `lsf` не проецирует ничего: его заголовок и изображение — лицо его кнопки, их рисует платформа. Контейнер с `lsf` проецируется так же, как любой контейнер, который рисует представление: компонент читает его `caption` и `image` из `data` и решает, куда поместить представление платформы.

Запись содержит `caption`, `image` — у свойства ещё `comment` — и, пока форма скрывает дочерний компонент, `hidden` — у свойства таблицы это вся запись его колонки — и находится в том же месте `data`, что и [опции отображения](#display-options), под тем же именем, по которому лежит значение дочернего компонента:

| Дочерний компонент с `lsf` | Где его запись | Ключ |
| --- | --- | --- |
| Свойство в **таблице** группы объектов, [рисуемое в каждой строке](#live-editor) | `data.<g>.<integrationSID>`, обычная запись колонки рядом с остальными колонками группы | Интеграционный SID свойства, `qty` |
| Свойство в **панели** или свойство пустой группы | `data.<g>.<integrationSID>`, в узле его группы (`data.<integrationSID>` для пустой группы), — там, где было бы его значение, если бы его рисовал React | Интеграционный SID свойства, `note` |
| Контейнер или любой другой компонент | `data.<componentSID>`, всегда на верхнем уровне | Его идентификатор компонента дизайна, `BOX(o)`, `GRID(o)` |

Свойство называется интеграционным SID — и в таблице, и в панели, и его запись, и его место. Запись лежит в узле его группы, там, где была бы запись свойства, которое рисует React, а `<Lsf>` называет панельное свойство тем путём, по которому эта запись читается: `<Lsf name="o.note"/>` — для `data.o.note`, `<Lsf name="note"/>` — для `data.note` пустой группы; хост он прячет, пока эта запись говорит `hidden`. Рендерер свойства таблицы в строке называется так же, `<Lsf name="o.quantity" row={row}/>` — для записи его колонки `data.o.quantity`, а строка говорит, какой это рендерер: она должна быть строкой этой группы — строка нижней группы дерева проходит и обрезается до пути к группе, как её принимает `change(row)` группы, — и запись колонки этот хост не прячет. Контейнер и любой другой компонент называется идентификатором дизайна, `<Lsf name="BOX(o)"/>` и `data['BOX(o)']`. Поэтому имя, по которому компонент размещает дочерний компонент, — это путь, по которому он читает его запись.

Такую запись, `data['<SID компонента>'] = { caption, image, hidden }`, на верхнем уровне `data` этого представления получает каждый компонент, который оно рисует, кроме свойства, которое оно несёт, — контейнер, объявленный через `NEW` и сгенерированный (`PANEL(o)`, `TOOLBAR(o)`, …) одинаково, грид (`GRID(o)`) или дерево (`GRID(TREE t)`), панель инструментов (`TOOLBARSYSTEM(o)`), — и каждый компонент с `lsf`, который оно размещает, кроме свойства, — кроме того, что лежит внутри контейнера с `lsf`: его платформа рисует целиком, и компонент туда не заглядывает. У самого контейнера `CUSTOM REACT` записи в его собственных `data` нет: его заголовок и изображение здесь никто не рисует — их рисует платформа вокруг контейнера, а у размещённого через `lsf` — представление, которое его размещает, по его записи у себя. Поле `hidden` записи следует за `SHOWIF` — собственным у компонента или у контейнера выше, — а не за тем, показывает ли представление этот компонент: у вкладки, которую представление не показывает, остаётся заголовок, а `hidden` нет. Пока оно есть в записи компонента с `lsf`, `<Lsf>` и `useLsf` скрывают узел, который его размещает, — узел получает `hidden` и остаётся: компонент по-прежнему размещён, поэтому продолжает читаться и возвращается вместе со своим `SHOWIF`. Запись входит в проецируемые `data`, поэтому динамический заголовок или изображение перерисовывают компонент как любое другое изменение данных.

Контейнер `CUSTOM REACT` подчиняется собственному `SHOWIF`, как любой другой компонент: платформа скрывает его блок. Внутри того, что рисует React, `tabbed`, `collapsed`, `popup` и `activated` ничего не делают: это содержимое раскладывает React, и полосы вкладок или заголовка сворачивания, к которым они бы относились, нет — вместо них у представления есть запись каждого контейнера, и показывает оно то, что хочет. `ACTIVATE TAB`, `COLLAPSE` или `EXPAND` из скрипта над компонентом там приводит к ошибке, как и над дочерним компонентом с `lsf`: его видимость принадлежит представлению.

`Lsf`, `useLsf`, `Caption` и `Image` — глобальные переменные времени выполнения, как и `List`, поэтому перед использованием в примерах ниже их нужно связать с локальными именами: `const { Lsf, useLsf, Caption, Image } = window.lsfusion;`.

Компонент называет каждый размещаемый дочерний компонент и сам рисует заголовок там, где ему нужно:

```jsx
export function Board(props) {
    const data = props.data;
    return <div className="board">
        <h3><Caption value={data['BOX(o)'].caption}/></h3>
        <Lsf name="BOX(o)"/>
        <h3><Caption value={data.comment.caption}/></h3>
        <Lsf name="comment"/>
    </div>;
}
```

### Размещение lsf-компонента {#lsf-child}

Дочерний компонент с `lsf` не обязан быть непосредственным потомком контейнера: он может лежать внутри контейнеров, которые представление рисует само, на любой глубине, и размещает его по имени всё тот же контейнер `CUSTOM REACT` над ним — поэтому дизайн группирует свои `lsf`-части так же, как их рисует представление, по страницам или секциям. Внутри контейнера с `lsf` отдельно не размещается ничего: такой контейнер платформа рисует целиком, и `lsf` на компоненте внутри него отклоняется при построении формы — если только его не размещает контейнер `CUSTOM REACT` внутри этого контейнера, как свой собственный.

Представление дочернего компонента с `lsf` переносится в *узел размещения* — узел DOM, которым владеет React и в который он никогда не отрисовывает дочерние элементы. React размещает представление относительно узла, которым владеет, и владеть им обязан, чтобы продолжать отрисовывать окружающее дерево. Какой это узел — единственное различие между двумя способами размещения:

```jsx
// узел создаёт платформа — <div> внутри секции
<section className="board-panel"><Lsf name="BOX(o)"/></section>

// узлом размещения становится собственный элемент компонента — на один узел меньше
<section {...useLsf('BOX(o)', { className: 'board-panel' })}/>
```

`<Lsf>` короче. `useLsf(name, { className, row })` — для элемента, который компонент отрисовывает и так: панели, карточки, ячейки сетки, — чтобы представление попадало прямо в него: он возвращает свойства, делающие этот элемент узлом размещения, — ref, переносящий туда представление, пометки узла и, пока запись дочернего компонента говорит об этом, `hidden`. Передайте их элементу разворотом (`{...}`), а класс элемента — в `useLsf`, а не самому элементу: `className`, записанный после разворота, заменяет тот, с которым объединены пометки.

Всё остальное у них общее. Узел размещения несёт класс `lsf-view` и атрибут `data-lsf-sid` с именем дочернего компонента, кто бы его ни создал: `<Lsf>` и `useLsf` отрисовывают их собственными свойствами, объединёнными с классом, который компонент даёт узлу, поэтому класс, меняющийся между отрисовками, их не стирает. Любой узел размещения стилизуется так, что представление его заполняет, каким бы ни был дочерний компонент, поэтому компонент задаёт размер узлу, а представление следует за ним:

```css
.board > .lsf-view[data-lsf-sid="BOX(o)"] { height: 260px; }
```

Размер задаёт компонент, так как атрибуты `width`, `height`, `fill` и выравнивания дочернего компонента с `lsf` **не** применяются: они задают его положение внутри штатного контейнера, а здесь окружающий элемент — это разметка самого компонента. Его `caption` и `image` дочерний компонент тоже не рисует — кроме действия, у которого это лицо его кнопки: они передаются компоненту в `data`, поэтому компонент, размещающий дочерние компоненты сам, рисует их там, где ему нужно, — иначе их не нарисует никто:

```jsx
<section className="board-panel">
    <h3><Image value={props.data['BOX(o)'].image}/><Caption value={props.data['BOX(o)'].caption}/></h3>
    <Lsf name="BOX(o)"/>
</section>
```

Рисуются через [`<Caption>`](#caption) и [`<Image>`](#image) — ровно затем они и есть: заголовок не всегда обычный текст, а изображение — либо адрес, либо готовый элемент.

Именно это делает возможной **полосу вкладок**, и ради этого запись и существует. Компонент, показывающий по одному дочернему компоненту с `lsf`, всё равно должен как-то назвать те, которые он не показывает, а называть их больше нечем. Работает это благодаря двум вещам: запись не следует за размещением — она есть с самого начала у каждого дочернего компонента с `lsf`, которого размещает контейнер, а её `hidden` следует за `SHOWIF`, а не за тем, показывает ли его представление, поэтому у закрытой вкладки есть подпись, — и заголовок продолжает читаться, пока тело скрыто, поэтому вычисляемый заголовок закрытой вкладки не устаревает.

```jsx
const TABS = ['BOX(o)', 'BOX(i)'];

export function LsfTabs(props) {
    const [active, setActive] = React.useState(TABS[0]);
    return <div className="lsf-tabs">
        <div className="lsf-tabs-strip" role="tablist">
            {TABS.map(sid => <button key={sid} role="tab" aria-selected={sid === active}
                                     onClick={() => setActive(sid)}>
                <Image value={props.data[sid].image}/><Caption value={props.data[sid].caption}/>
            </button>)}
        </div>
        <Lsf key={active} name={active} className="lsf-tabs-body"/>
    </div>;
}
```

Отрисовка только активного дочернего компонента, а не сокрытие остальных, — это и есть то, из-за чего закрытые вкладки перестают читаться, см. [ниже](#lsf-child). Вкладки нужно делать над `BOX` группы, а не над её `GRID`: заголовок и изображение есть только у контейнера и у свойства, поэтому в записи размещённого `GRID(o)` нет заголовка — она говорит только о том, скрывает ли форма грид.

Полоса вкладок над детьми обоих видов держит одно имя на вкладку — то, по которому она размещает дочерний компонент, — и по нему же читает его запись: идентификатор дизайна — на верхнем уровне, имя свойства — как путь:

```jsx
const TABS = ['BOX(o)', 'o.note'];   // контейнер и панельное свойство o с lsf
const entryOf = (data, name) => {
    const dot = name.lastIndexOf('.');
    return name in data || dot < 0 ? data[name] : data[name.slice(0, dot)][name.slice(dot + 1)];
};
// полоса: <Caption value={entryOf(props.data, sid).caption}/>; тело: <Lsf key={active} name={active}/>
```

Размещение ограничено следующими правилами:

- Каждый дочерний компонент с `lsf` размещается не более чем одним узлом. Не размещённый ни одним узлом дочерний компонент не показывается. Повторный узел сообщает о себе на странице и в консоли, а первый сохраняет за собой дочерний компонент.
- Компонент внутри контейнера, у которого есть собственное представление, но нет `lsf`, — перенесённые внутрь тулбар или блок фильтров группы, — не показывает никто, и консоль один раз сообщает об этом вместе со способом исправить.
- Узел должен попасть на страницу. Узел, который к концу создавшей его отрисовки так и остался вне документа, отдаёт дочерний компонент: представление возвращается в ожидание, его получает `<Lsf>` с тем же именем, который на странице есть, а в консоль пишется, какое имя было отдано. Узел, добавляемый порталом в эффекте, к этому моменту уже на странице и размещается как обычно.
- Узел, который отрисовывает `<Lsf>`, содержит представление lsFusion, поэтому он должен оставаться пустым: ему задаются класс или стиль, но не дочерние элементы.
- `lsf` можно ставить только на компонент, который размещает контейнер `CUSTOM REACT`, — внутри него и не внутри контейнера с `lsf` на пути к нему. В любом другом месте форма отвергается при сборке (компонент, удалённый из дизайна, не проверяется).

Размещение, которое не может сработать, сообщает об этом в самом узле, а не только в консоли: имя, не называющее ничего внутри контейнера (и внутри контейнеров, которые он рисует сам), компонент без `lsf`, второй узел для того же дочернего компонента, имя, переданное с `row`, которое не называет свойство таблицы с `LSF` из группы, которую рисует это представление, `row` другой группы, и `row`, не являющийся строкой, — каждый случай выводит своё сообщение в узел, в элементе с классом `lsf-view-error`. Собственный класс узла остаётся таким, каким его задал компонент.

Представление сообщает серверу, какие дочерние компоненты с `lsf` оно размещает, — их набор, а не монтирования и размонтирования, которые его изменили: набор вычисляется после каждого изменения размещения и один раз после первой отрисовки компонента, а отправляется только то, что изменилось. Дочерний компонент, у которого есть узел размещения — с его представлением или в ожидании его, — размещён. Дочерний компонент, который не размещает ни один `<Lsf>`, не читается — так же, как неактивная вкладка или свёрнутый контейнер, — кроме того, что его подписывает: его заголовок, изображение и комментарий читаются и дальше, как заголовок неактивной вкладки, чтобы компонент мог по-прежнему его называть. Его группа перестаёт читаться, только если это было последнее место её отображения на форме. Поэтому компонент, показывающий по одному дочернему компоненту, отрисовывает только его, а не прячет остальные средствами CSS: скрытый через CSS компонент для сервера остаётся размещённым и продолжает читаться. По той же причине видимость дочернего компонента с `lsf` принадлежит только компоненту: его атрибуты `collapsible`, `collapsed` и `activated` игнорируются, а `COLLAPSE` / `EXPAND` или `ACTIVATE TAB` из скрипта над ним приводит к ошибке.

### Живой редактор в каждой строке {#live-editor}

Дочерний компонент с `lsf` рисуется один раз. Свойство таблицы, помеченное в `FORM` как `LSF`, рисуется один раз **на строку**, поэтому компонент может поместить настоящий редактор lsFusion в каждую отрисовываемую им строку — вместо того чтобы показывать значение и строить редактирование самому:

```lsf
FORM orders 'Orders'
    OBJECTS o = Order
    PROPERTIES(o) number READONLY, date
    PROPERTIES(o) quantity LSF, note LSF
;

DESIGN orders {
    NEW board {
        custom = 'OrderBoard';
        MOVE BOX(o);                  // строки рисует React, по data.o
    }
}
```

`LSF` говорит, что свойство является компонентом, а не значением. Где оно размещается, не говорится — и не может: у свойства таблицы нет собственного места в дизайне, а его отрисовщики попадают в строки, поэтому размещает их тот компонент, который эти строки рисует. Здесь это компонент, которому группу отдал `MOVE BOX(o)`. `MOVE` свойства таблицы отклоняется при построении формы — с `LSF` или без. Компонент называет свойство так, как ключуется запись его колонки, — с группой — и передаёт строку:

```jsx
{data.o.list.map(row => (
  <tr key={row.key}>
    <td>{row.number.value}</td>
    <td><Lsf name="o.quantity" row={row}/></td>
    <td><Lsf name="o.note" row={row}/></td>
  </tr>
))}
```

Передавайте объект строки из проецируемых данных — по одному ключу строку восстановить нельзя. Одно и то же свойство размещается один раз на строку, и только один раз.

Что автор получает и что остаётся за ним:

- Редактор принадлежит платформе со всем, что из этого следует: редактирование, `READONLYIF`, `BACKGROUND` и остальные опции ячейки, — и всё это вычисляется для **этой** строки.
- Свойство уходит из строк: теперь это компонент, поэтому `row.quantity` там нет, и члена для него у контроллера нет — значения рисует и правит платформа. Запись его колонки остаётся — обычная, в `data.o.quantity`: `caption`, `image`, `footer`, `comment`, `type`, `hidden`, — и `properties` её перечисляет. Его редакторы размещаются по тому же имени, `o.quantity`, поэтому имя у него должно быть: свойство, объявленное с `NOEXTID`, отклоняется при построении формы. Если значение нужно ещё и как данные, объявите второе, обычное свойство.
- Заголовок в строке не рисуется, как и комментарий: своих у построчных редакторов нет. Как и заголовок дочернего компонента с `lsf`, оба приходят в узле колонки группы — `data.o.quantity.caption`, `data.o.quantity.comment`, — поэтому компонент размещает их там, где нужно, обычно один раз, в шапке. У действия записи колонки нет вовсе: его заголовок и изображение остаются на его кнопках, это их лицо.
- Отрисовщик существует для каждой строки, которую группа показывает сейчас, независимо от того, отрисовывает компонент эту строку или нет. Строка, ушедшая за пределы прокрутки, свой редактор сохраняет. Теряет его только строка, покидающая этот набор.

Объявление отклоняется с указанием свойства, когда работать оно не может: на свойстве таблицы, группа которого не отрисовывается контейнером `CUSTOM REACT` (построчные редакторы было бы некому размещать), и на свойстве таблицы, сгруппированном в колонки (построчный редактор не может адресовать ячейку на пересечении строки и колонки).

### Расширение контейнера с lsf-компонентами

Другой модуль добавляет в контейнер дочерний компонент из `DESIGN`:

```lsf
EXTEND FORM orders PROPERTIES() rating;
DESIGN orders {
    board { MOVE PROPERTY(rating) { lsf = TRUE; } }
}
```

Сам по себе компонент его не подхватит. Каждый дочерний компонент с `lsf` размещается тем `<Lsf>`, который его называет, поэтому дочерний компонент, не названный ни одним `<Lsf>`, не показывается, и такое добавление требует правки JSX: расширение `DESIGN` объявляет дочерний компонент, а компонент решает, где он окажется. Расположение из `DESIGN` тоже не расширяется: композицию React там изменить нельзя. Чтобы изменить расположение, компонент заменяется целиком через `custom = 'OtherBoard'`, а дочерние компоненты остаются объявленными в `DESIGN`.

### Выбор между компонентом React и HTML-шаблоном

Компонент, который только размещает дочерние компоненты с `lsf` и ничего не читает из `props.data`, делает то же, что и классический пользовательский контейнер: HTML-шаблон располагает те же дочерние компоненты по своим местам `<Lsf:name>`, без рантайма React и без узла-хоста на каждый из них. Если `lsf` стоит на всех дочерних компонентах контейнера, в `props.data` нет ни значений групп, ни значений свойств, поскольку компонент с `lsf` не проецируется, — только записи `{ caption, image, hidden }` дочерних компонентов в `props.data`.

Шаблону не даётся никаких данных. Он размещает то, что рисует платформа, по имени, а всё остальное в нём написано вручную: он не может прочитать ни заголовок потомка, ни его значок, ни заголовок самого контейнера. Заголовки, которые он показывает, рисует платформа: потомок-свойство рисуется по частям (если у него не задано `inline = FALSE`) — его заголовок и комментарий становятся отдельными местами, `<Lsf:PROPERTY(qty).caption>` и `<Lsf:PROPERTY(qty).comment>`, которые шаблон может поставить внутрь своей разметки, например в заголовок раздела, — любой другой потомок несёт свой заголовок внутри размещённого представления, а заголовок и значок самого контейнера платформа рисует рядом с контейнером, а не внутри шаблона. Поэтому своя разметка, которой нужен вычисляемый приложением заголовок — как собственный текст или как заголовок контейнера, — это та граница, за которой шаблона уже не хватает.

И тот и другой называют свои дочерние компоненты, поэтому ни один из них не расширяется одним только `DESIGN`: чтобы добавить дочерний компонент, нужно изменить JSX или строку шаблона. Компонент React оправдан тогда, когда расположение вычисляется — дочерние компоненты размещаются по условию, сетка выводится из данных, прочитанных через `useData`, или разметка берётся из библиотеки компонентов, — а строка шаблона принадлежит объявившему её модулю и заменяется только целиком. Компонент нужен и тогда, когда разметка должна показать то, что несёт проекция, — а для контейнера и потомка с `lsf` это его `caption` и `image`.

### Интерактивность

Чтобы читать и изменять состояние формы из компонента — выбирать строку, изменять свойство, вызывать действия — используется `props.controller`. Его методы описаны в [How-to: Контроллер пользовательского представления](How-to_Custom_view_controller.md).

Компонент, который рисует собственное поле, также сообщает форме, что пользователь в нём редактирует, чтобы во время набора `ENTER` не переводил фокус на следующий компонент, а `ESCAPE` не закрывал окно — см. [Объявление редактирования](How-to_Custom_view_controller.md#editing). Компоненту, который своих полей не рисует, объявлять нечего.

### Живые данные {#live-data}

Данные, которые меняются, пока форма открыта, — котировки, очередь, монитор — обновляет сама форма, а не таймер в компоненте. [Событие `SCHEDULE`](../paradigm/Form_events.md) формы выполняет действие раз в заданное число секунд, а изменившееся платформа доставляет через `props.data`, как любое другое изменение:

```lsf
FORM quotes 'Котировки'
    OBJECTS q = Quote
    PROPERTIES(q) READONLY symbol, price, changedAt
    EVENTS ON SCHEDULE PERIOD 2 formRefresh()
;

DESIGN quotes {
    BOX(q) {
        custom = 'QuoteBoard';
    }
}
```

`System.formRefresh[]` перечитывает всё, что показывает форма, поэтому ответ несёт всю форму на каждом запуске. Обновления одной группы объектов нет: `System.forceUpdate[STRING]` лишь применяет накопленное обновление группы в режиме ручного обновления (атрибут дизайна `enableManualUpdate`) и ничего не делает для группы, обновляемой автоматически. Поэтому живое табло держат отдельной формой только с теми свойствами, которые оно рисует, а период берут не короче, чем требуют данные.

Запуск по расписанию отличается от запроса, который компонент сделал бы сам. Собственный таймер компонента, вызывающий `controller.refresh.exec()`, опрашивает сервер так же, как нажатие на форме: синхронным запросом, блокирующим ввод до своего завершения, если действие не выведено с `NOWAIT`, — и, как показывает третий пункт, продолжает опрос на скрытой форме.

- **Не блокирует пользователя.** Веб-клиент отправляет его асинхронным запросом, не блокируя ввод и без [индикатора ожидания](../paradigm/Interactive_view.md#busy), который получает синхронный запрос, так что пользователь продолжает работать, пока форма перечитывается.
- **Выполняется, только пока форма на экране.** Для формы в фоновой закладке, формы, которую компонент [окна форм](#forms-window) никуда не поместил, или формы под модальным диалогом запуск пропускается. Таймер продолжает отсчёт, и следующий запуск происходит, когда форма снова показана.
- **Скрытая форма остаётся смонтированной.** Фоновая закладка и неразмещённая форма скрыты, а не закрыты, поэтому компонент по-прежнему смонтирован, и его собственный `setInterval` продолжает срабатывать — и обращаться к серверу, — пока расписание формы приостановлено. Поэтому обновление принадлежит форме, а не компоненту. Таймер, который компоненту всё же нужен (анимация, обратный отсчёт), как обычно снимается в очистке эффекта, но эта очистка выполняется при закрытии формы, а не при её скрытии.

### Окно навигатора {#navigator-window}

Компонент React может рисовать и окно навигатора — само меню — вместо стандартной панели. Имя компонента задаётся [`WINDOW`](../language/WINDOW_statement.md), а данными компонента становятся элементы, помещённые в это окно:

```lsf
WINDOW appMenu VERTICAL POSITION(0, 6, 20, 94) HIDETITLE CUSTOM 'AppMenu';

NAVIGATOR {
    NEW FOLDER sales 'Продажи' WINDOW appMenu PARENT {
        NEW orders;
        NEW invoices;
    }
}
```

```jsx
function AppMenu({ data, controller }) {
    return <nav>{data.root.map(name => {
        const e = data.byName[name];
        return <button key={name} className={e.selected ? 'on' : ''}
                       onClick={ev => controller.activate(name, ev.nativeEvent)}>{e.caption}</button>;
    })}</nav>;
}
```

Компонент можно задать и уже существующему окну, в том числе стандартной панели, — тогда навигатор не перестраивается вовсе, меняется только его отрисовка:

```lsf
EXTEND WINDOW System.toolbar CUSTOM 'AppMenu';
```

`props.data` — собственные элементы этого окна по [каноническому имени](../paradigm/Naming.md#canonicalname). Канонические имена содержат точки, поэтому они являются ключами отображения, а не полями:

| Поле | Значение |
| --- | --- |
| `root` | Канонические имена элементов, рисуемых на верхнем уровне, в порядке отображения |
| `byName` | Каждый элемент по каноническому имени |

а каждый элемент содержит:

| Поле | Значение |
| --- | --- |
| `name` | Собственное каноническое имя, чтобы компонент, получивший одну запись, мог обратиться к элементу |
| `caption`, `elementClass` | Заголовок и CSS-класс, текущие — выражение `HEADER` или `CLASS` применяется по мере изменения |
| `image` | Значок, рисуется через `<Image value={e.image}/>` — см. [ниже](#image) — либо `null` |
| `folder` | Является ли элемент папкой, а не действием |
| `hidden` | Скрыт ли он сейчас через `SHOWIF`. В отличие от стандартной панели, которая такой элемент просто не рисует, проекция его сохраняет, и компонент сам решает, как с ним поступить |
| `selected` | Является ли он выбранным элементом **этого окна** |
| `children` | Канонические имена его потомков, которые рисует это окно |

Элемент, объявленный [`LSF`](../language/NAVIGATOR_statement.md), рисует платформа, поэтому то, что она рисует, не проецируется: в его записи остаются `name`, `caption`, `image`, `children` и `lsf: true`, и больше ничего.

Окно получает те элементы, за которые отвечает: элемент, ушедший в другое окно, и поддерево, отсечённое потому, что его родитель не выбран, отсутствуют — по тому же правилу, по которому определяется содержимое стандартной панели. Всё, что это правило оставило, проекция сохраняет, скрытое оно или нет. Компонент отрисовывается, когда навигатор определил элементы окна, и окно без элементов тоже отрисовывается — с пустым `root`. `props.controller` — контроллер навигатора, чей [`activate`](How-to_Custom_view_controller.md#navigator-controller) делает то же, что нажатие на элемент: выбирает папку либо выполняет действие.

Поэтому окно может получить элементы, которых модуль не объявлял. `WINDOW` у папки называет окно её потомков, и потомок, попавший в другое окно, рисуется там, пока папка выбрана. В штатном приложении так устроено «Администрирование»: сама папка лежит в `System.system`, а её разделы объявлены с `WINDOW toolbar PARENT`, поэтому, пока она выбрана в верхней панели, их вместе с их потомками рисует окно `System.toolbar` — после `EXTEND WINDOW System.toolbar CUSTOM` это ваш компонент. Компонент, который рисует только известные ему элементы, такие разделы потеряет. Всё, что окну досталось, обходится через `root` и `children`.

Компонент рисует только веб-клиент на компьютере. Мобильный веб-клиент и десктоп-клиент отрисовывают для этого окна своё стандартное меню, поэтому навигатор остаётся рабочим в каждом из них.

#### Стандартная кнопка {#standard-button}

Элемент, который компонент не хочет рисовать сам, помещается через `<Lsf name/>` — тот тег, которым на форме размещается потомок дизайна, где `name` — каноническое имя элемента. Платформа ставит внутрь свою кнопку, со своим значком, заголовком, подсказкой и поведением при нажатии. Сам узел остаётся таким, каким его нарисовал компонент, без пометок, которые получает узел на форме:

```jsx
const { Lsf } = window.lsfusion;

function AppMenu({ data, controller }) {
    return <nav>
        <Lsf name="Sale.sales" className="menu-main"/>
        {data.root.filter(name => name !== 'Sale.sales').map(name =>
            <button key={name} onClick={ev => controller.activate(name, ev)}>{data.byName[name].caption}</button>)}
    </nav>;
}
```

Элемент должен быть объявлен `LSF` в [`NAVIGATOR`](../language/NAVIGATOR_statement.md) — переход обратно объявляется на стороне навигатора так же, как `lsf = TRUE` объявляет его на форме:

```lsf
NAVIGATOR {
    Sale.sales LSF;
}
```

Элемент с `LSF`, которого не назвал ни один `<Lsf>`, не показывается — так же, как на форме. Четыре ошибки сообщаются прямо на странице: имя, которого нет ни у одного элемента навигатора, имя без `LSF` — такой элемент компонент должен рисовать сам, по проекции, — имя элемента, который рисует другое окно, и имя, которое размещает второй `<Lsf>`. Имя, которое окно сейчас просто не рисует — элемент, скрытый `SHOWIF`, отсечённый потому, что его родитель не выбран, — ошибкой не является и не сообщается: место остаётся пустым и ждёт, а заполняется, как только окно начнёт рисовать этот элемент. То, в каком окне рисуется элемент, к таким случаям не относится: ждать кнопку, которой владеет другое окно, пришлось бы вечно.

Почти стандартное меню пишется так: по одному `<Lsf>` на каждый элемент, который рисует платформа, и разметка только для тех, которые компонент рисует сам.

#### HTML-шаблон вместо компонента {#navigator-template}

Окну, меню которого нужна только своя разметка, вместо имени компонента задаётся HTML-шаблон — [тот же](../language/WINDOW_statement.md), который принимает контейнер `custom`, где место `<Lsf:name>` принимает стандартную кнопку элемента. Имя разрешается так же, как любое другое имя в модуле, поэтому писать его полностью не нужно, а место пишется открытым — закрыть его нельзя:

```lsf
EXTEND WINDOW System.toolbar CUSTOM
    '<div class="menu"><div class="menu-head">Справочники</div><Lsf:items><Lsf:partners></div>';
```

Элемент должен быть объявлен раньше шаблона, который даёт ему место, — блок `NAVIGATOR`, создающий его, идёт выше. Имя, которое ни во что не разрешается, — ошибка при чтении модуля, поэтому опечатка останавливает приложение, а не оставляет меню без пункта.

Элемент, которому шаблон не дал места, не рисуется, поэтому шаблон называет всё, что показывает, и `LSF` ни на одном из них не нужен — шаблон размещает только отрисовки самой платформы.

Шаблон можно и вычислять: если вместо литерала задано свойство, он пересчитывается по мере изменения значения, и окно рисуется заново по новой разметке, поэтому меню может перестраиваться и без компонента. Вычисляемый шаблон ничто не разрешает, поэтому его места называют элементы полностью, каноническим именем. Компонент остаётся нужен тогда, когда разметка зависит от того, что компонент читает сам.

### Окно форм {#forms-window}

Компонент React может рисовать и окно, в котором открываются формы, вместо стандартных вкладок. Окну [`WINDOW`](../language/WINDOW_statement.md) `System.forms` задаётся имя компонента, а его данными становятся открытые формы - и так же любому другому окну `FORMS`, которое объявило приложение: ему передаются формы, открытые в него оператором `SHOW ... WINDOW windowName`:

```lsf
EXTEND WINDOW System.forms CUSTOM 'FormsBoard';
```

```jsx
const { Lsf, Caption } = window.lsfusion;

function FormsBoard({ data, controller }) {
    const current = data.open.find(name => data.byName[name].selected);
    return <div className="board">
        <div className="board-bar">{data.open.map(name => {
            const e = data.byName[name];
            return <span key={name} className={e.selected ? 'on' : ''}>
                <a onClick={() => controller.select(name)}><Caption value={e.caption || '...'}/></a>
                {!e.blocked && <a onClick={() => controller.close(name)}>x</a>}
            </span>;
        })}</div>
        {current && <Lsf key={current} name={current} className="board-current"/>}
    </div>;
}
```

Форму компонент не рисует никогда: он рисует место для той формы, которую хочет показать, а платформа переносит туда её собственное представление. Этим местом и является `<Lsf name/>`, где `name` — имя, которое проекция даёт форме. Представление формы он размещает так же, как размещает [дочерний элемент дизайна](#lsf-child) и [элемент навигатора](#standard-button), и ошибки здесь выводятся те же. Как и узел дочернего элемента дизайна, это место несёт метки — класс `lsf-view` и `data-lsf-sid` с именем формы, — а представление формы заполняет его.

`props.data` — открытые формы и состояние самого окна. Компонент отрисовывается сразу вместе с окном, до открытия какой-либо формы, — `open` тогда пуст, — поэтому то, что показывается, пока ничего не открыто, рисует он сам:

| Поле | Значение |
| --- | --- |
| `open` | Имена открытых форм в том порядке, в котором их показывает стандартная полоса |
| `byName` | Каждая форма по имени |
| `editMode` | Имя выбранного режима редактирования — того, который выбирает кнопка режима на панели платформы и который сохраняется между сеансами. Режим, включённый удержанием Ctrl, Shift или Alt, действует, пока клавиша нажата, и `editMode` не меняет |
| `editModes` | Все режимы редактирования в том порядке, в котором их предлагает кнопка режима |
| `fullScreen` | Развёрнуто ли окно форм на весь экран |

и каждая форма несёт:

| Поле | Значение |
| --- | --- |
| `name` | Собственное имя, чтобы компонент, которому передали только запись, всё равно мог обратиться к форме |
| `canonicalName` | [Каноническое имя](../paradigm/Naming.md#canonicalname) формы — для компонента, который рисует конкретную форму по-своему |
| `caption`, `image` | Заголовок и значок, текущие: заголовок, который показывает вкладка, и его значок. Рисуются через [`<Caption value={e.caption}/>`](#caption) и [`<Image value={e.image}/>`](#image) |
| `selected` | Является ли форма текущей — той, в которой работает клавиатура |
| `loading` | Не пришла ли форма ещё с сервера. Пока не пришла, `caption` — тот, который нёс запрос на её открытие, а `image` пуст; остальные поля записи на месте, как всегда |
| `blocked` | Открыта ли поверх этой формы форма, вызванная из неё. Такую форму закрыть нельзя — поэтому стандартная вкладка выключает у неё кнопку закрытия |

а каждый режим редактирования в `editModes` — то, чем его показывает кнопка режима:

| Поле | Значение |
| --- | --- |
| `name` | Собственное имя режима — то, которое принимает `setEditMode`, и то, с которым сравнивается `editMode` |
| `caption`, `image` | Название режима и его значок. Рисуются через [`<Caption value={m.caption}/>`](#caption) и [`<Image value={m.image}/>`](#image) |

`props.controller` делает то, что с открытой формой может сделать только платформа: `select(name)` делает её текущей — так же, как щелчок по её вкладке, — а `close(name)` просит её закрыться, как её кнопка закрытия. Закрытие — это просьба: форма с несохранёнными изменениями сначала спросит пользователя и может остаться открытой, поэтому форма исчезает из `open` тогда, когда действительно закрылась, а не когда был вызван `close`.

Форма, которую компонент никуда не поместил, остаётся **открытой и скрытой** — ровно то, чем уже является фоновая вкладка: стандартная полоса просто прячет формы, которые не показывает. Поэтому компонент, помещающий только текущую форму, даёт приложение без вкладок, в котором все открытые ранее формы никуда не делись, и, поместив форму снова, её видно в том состоянии, в котором её оставили. Закрывается форма только через `close(name)` или `closeAll()` — либо так же, как она закрывается без компонента.

Собственная панель платформы — режим редактирования, полный экран, мобильное меню — расположена в стандартной полосе вкладок, поэтому окно, которое рисует компонент, её не показывает. То, что она делает с самим окном, компонент делает через контроллер: `setEditMode(name)` выбирает режим редактирования — так же, как кнопка режима, — где `name` — имя режима из `editModes`, а `toggleFullScreen()` разворачивает окно форм на весь экран и возвращает обратно — так же, как кнопка полного экрана и ALT+F11. Отсюда же доступно и то, что предлагает контекстное меню стандартной вкладки: `closeAll()` просит закрыться каждую открытую форму, начиная с последней в этом порядке. Закрытие каждой из них — такая же просьба, поэтому форма, которая не закрылась, остаётся открытой, а остальные закрываются. Выбранный режим и полный экран платформа знает сама, поэтому она их и проецирует: режим, выбранный компонентом, и полный экран, включённый по ALT+F11, компонент видит одинаково — в `props.data`. Мобильное меню компоненту не нужно: на мобильном веб-клиенте окно форм рисует платформа.

Компонент рисует только десктопный веб-клиент. Мобильный веб-клиент и десктоп-клиент оставляют своё стандартное окно форм.

### Шапка приложения {#application-header}

Шапка с полем поиска, которое находит записи, - это форма: ей нужны живая проекция, сессия, в которой живёт запрос, сортировка и постраничность, и способ открыть найденное. Поэтому она строится как форма и открывается в собственное окно - [`WINDOW ... FORMS`](../language/WINDOW_statement.md) над областью форм - оператором [`SHOW ... WINDOW windowName`](../language/SHOW_operator.md):

```lsf
// окно, в котором живёт шапка: одна форма, нарисованная одна над областью форм, не выше этой формы
WINDOW header 'Шапка' FORMS AUTOSIZE POSITION(20, 6, 80, 10) HIDETITLE;

// чем шапка ищет и что находит
query 'Поиск' = DATA LOCAL ISTRING[100] ();
found (Customer c) = isISubstring(name(c), query()) OR isISubstring(city(c), query());

// что делает найденная запись: открывается обычной закладкой в System.forms
openCustomer 'Открыть' (Customer c) { SHOW customer OBJECTS c = c NOWAIT; }

// шапка - это ФОРМА: запрос - её свойство, найденное - её группа объектов, сессия - её собственная
FORM appHeader 'Шапка'
    PROPERTIES() query
    OBJECTS c = Customer
    PROPERTIES(c) READONLY name, city
    PROPERTIES(c) openCustomer
    FILTERS found(c)
    ORDERS name(c)
;

// рисует её компонент, по обычной проекции формы
DESIGN appHeader {
    // это шапка, а не документ: никаких «Сохранить», «Отменить», «ОК», «Закрыть»
    REMOVE TOOLBARBOX;
    NEW search {
        custom = 'Search';
        fill = 1;               // контейнер занимает окно, а не сжимается по содержимому
        MOVE PROPERTY(query());
        MOVE BOX(c);
    }
}

// открывается один раз, при старте клиента; перезагрузка страницы - это снова старт клиента
onWebClientStarted() + {
    SHOW appHeader WINDOW header NOWAIT;
}
```

```jsx
// здесь ничего не запрашивается, не кэшируется и не инвалидируется: запрос и найденное принадлежат форме
const { useData, useController } = window.lsfusion;

function Search() {
    const data = useData();
    const controller = useController();
    const query = data.query.value || '';
    const rows = data.c.list;
    const input = React.useRef(null);

    // что поле отправило последним, пока проекция этого не показала: до тех пор проекция отстаёт от поля
    const [sent, setSent] = React.useState(null);
    const send = value => {
        setSent(value);
        controller.query.change(value);
    };
    // поле следует за запросом только если его изменил кто-то другой, и никогда пока пользователь в нём, -
    // поэтому догоняет его, когда пользователь из поля уходит
    const follow = () => {
        if (input.current && sent === null && input.current.value !== query && document.activeElement !== input.current)
            input.current.value = query;
    };
    React.useEffect(() => {
        if (query === sent)
            setSent(null);
        follow();
    }, [query, sent]);

    // где рисуются результаты: под полем и следом за ним
    const [box, setBox] = React.useState(null);
    const place = React.useCallback(() => {
        if (!input.current) return;
        const r = input.current.getBoundingClientRect();
        setBox({ left: r.left, top: r.bottom + 2, width: r.width });
    }, []);
    React.useEffect(place, [query, rows.length, place]);
    React.useEffect(() => {
        const onKey = e => {
            if (e.key !== 'Escape') return;
            if (input.current) input.current.value = ''; // пользователь в поле, поэтому follow() его не трогает
            send('');
        };
        window.addEventListener('resize', place);
        window.addEventListener('scroll', place, true);
        document.addEventListener('keydown', onKey);
        return () => {
            window.removeEventListener('resize', place);
            window.removeEventListener('scroll', place, true);
            document.removeEventListener('keydown', onKey);
        };
    }, [place, controller]);

    return <div className="search">
        <input className="search-input" maxLength={100} placeholder="Поиск клиентов…" ref={input}
               onChange={e => send(e.target.value)} onBlur={follow}/>
        {query && box && ReactDOM.createPortal(
            <div className="search-results" style={{ position: 'fixed', left: box.left, top: box.top, width: box.width, zIndex: 1000 }}>
                {rows.length === 0 && <div className="search-empty">Ничего не найдено</div>}
                {rows.map(row =>
                    <div key={row.key} className="search-row" onClick={() => controller.c.openCustomer.exec(row)}>
                        <b>{row.name.value}</b> <span className="search-city">{row.city.value}</span>
                    </div>)}
            </div>, document.body)}
    </div>;
}

window.lsfusion.custom.register('Search', Search, 'reactView');
```

Всё, что показывает компонент, приходит из проекции, которую он читает через `useData()`: запрос - это `data.query.value`, найденное - `data.c.list`, и платформа держит его актуальным по мере изменения запроса: `controller.query.change(…)` - обычное редактирование, и `FILTERS` формы применяются заново.

Поле ввода намеренно **неуправляемое** - ему не передаётся `value={query}` - и это единственное, что представление такого рода обязано сделать правильно. Значение, которое отправляет поле, проекция показывает сразу, потому что платформа показывает правку до ответа сервера, и держит последнее из отправленных, пока приходят ответы на предыдущие: ответ сервера заменяет его, только если сервер сохранил иное или отклонил изменение. Но проекция может измениться и пока пользователь печатает - запрос запишет кто-то другой или поправит сервер, - и управляемое React поле перерисовывалось бы из неё прямо под рукой пользователя. Поэтому набранным текстом владеет поле, а за проекцией оно следует только когда запрос изменил кто-то другой и пользователь не находится в поле, и догоняет её, когда пользователь из поля уходит. `sent` хранит значение, которое поле отправило последним, пока проекция его не покажет, чтобы поле не приняло своё изменение за чужое. Это рассчитано на то, что запрос сохраняется так, как набран: это свойство `DATA`, а `maxLength` не даёт ввести больше, чем вмещает его `ISTRING[100]`. Клик выполняет действие, нарисованное на группе, для кликнутой строки - `controller.c.openCustomer.exec(row)` - и запись открывается там, где форма открывается по умолчанию, - закладкой в `System.forms`. Шапка остаётся: окно `FORMS` рисует одну форму за раз, поэтому форма, которую приложение позже откроет `WINDOW header`, заменит её, а `WINDOW` без окна её не тронет.

Двумя вещами шапка перестаёт выглядеть документом. `REMOVE TOOLBARBOX` убирает собственную панель формы - сохранять, отменять и закрывать здесь нечего, а кнопки рисует именно этот контейнер. (`POPUP` и `EMBEDDED` получают это даром: `SHOWIF` каждой системной кнопки собран из свойств окружения формы, а встроенный редактор выставляет `isEditing`, которое эти условия отрицают. Форма, нарисованная шапкой, встроенным редактором не является, поэтому говорит о своём желании в дизайне.) Результаты рисуются **порталом в тело страницы**, а не внутри контейнера, и это второе, что представление такого рода обязано сделать правильно. Окно по замыслу невысокое и обрезает то, что рисует его форма: список, оставленный внутри полосы шапки, срезается после первой строки. Большой `z-index` тоже не спасает: элемент самого окна - это контекст наложения (`position: relative; z-index: 0`), поэтому слой внутри него никогда не поднимется над соседними окнами. Портал уходит от обоих ограничений. После этого слой позиционируется по `getBoundingClientRect()` поля и обязан следовать за ним при изменении размера окна и прокрутке, а по Escape - исчезать.

Именно `AUTOSIZE` у окна не даёт полосе стать высокой и пустой: шапка ровно такой высоты, как её форма, - здесь это одно поле ввода, - и при этом растягивается поперёк, а контейнер с `fill = 1` внутри неё занимает эту высоту, а не сжимается по своему содержимому. Размер окна задаёт раскладка, а не форма в нём, поэтому без этой опции полоса занимает ту долю высоты, которую запрашивает `POSITION`, пуста она или полна. Учтите и то, что клиент запоминает размер, который пользователь потянул мышью, и восстанавливает его поверх объявленного: вернуть объявленные размеры можно действием `Service.resetWindowsLayout`. Про `POSITION` полезно знать две вещи, прежде чем шапка покажется неправильной. Числа - это не прямоугольник, в котором рисуется окно, а способ, которым раскладка делит пространство: шапка с `POSITION(20, 6, 80, 10)` становится полосой справа от тулбара и над `System.forms`. А пока навигатор не закреплён полностью, его панель - это оверлей, висящий над соседними окнами: клик, нацеленный в шапку, попадает в меню под ней и выполняет то, что выполняет этот пункт меню.

Чего маршрут через форму не даёт - свежести между соединениями: форма не видит того, что закоммитило другое соединение, пока не перечитает данные, поэтому шапка, которая должна это показывать, добавляет форме [`EVENTS ON SCHEDULE PERIOD n formRefresh()`](../paradigm/Interactive_view.md). И шапку рисует только десктопный веб-клиент: мобильный веб-клиент и десктоп-клиент рисуют одно окно `System.forms` и открывают шапку там, закладкой, поэтому приложение, которое их обслуживает, оставляет дизайн шапки пригодным и как обычной формы.

### Окно сообщений {#log-window}

Компонент React может рисовать и окно, в котором появляются сообщения пользователю, вместо стандартной панели. Окну [`WINDOW`](../language/WINDOW_statement.md) `System.log` задаётся имя компонента, а его данными становятся выведенные сообщения:

```lsf
EXTEND WINDOW System.log CUSTOM 'MessageLog';
```

```jsx
const { Lsf } = window.lsfusion;

function MessageLog({ data, controller }) {
    return <div className="log">
        <a className="log-pin" onClick={() => controller.togglePin()}>pin</a>
        {data.messages.map(name => {
            const m = data.byName[name];
            return <div key={name} className={m.failed ? 'log-failed' : 'log-ok'}>
                <div className="log-line">{new Date(m.time).toLocaleTimeString()} {m.caption}</div>
                <Lsf name={name}/>
            </div>;
        })}
    </div>;
}
```

Сообщение компонент не рисует никогда: сообщение — это разметка, которую построила платформа (текст со значком или таблица, выведенная действием рядом с ним), поэтому компонент рисует место для каждого сообщения, которое хочет показать, а платформа переносит туда эту разметку. Этим местом и является `<Lsf name/>`, где `name` — имя, которое проекция даёт сообщению. Разметку сообщения он размещает так же, как размещает [дочерний элемент дизайна](#lsf-child), [элемент навигатора](#standard-button) и [открытую форму](#forms-window).

`props.data` — выведенные сообщения, и компонент отрисовывается ещё до прихода первого из них, с пустым `messages`:

| Поле | Значение |
| --- | --- |
| `messages` | Имена выведенных сообщений, начиная с последнего — в том порядке, в котором их показывает стандартная панель |
| `byName` | Каждое сообщение по имени |

и каждое сообщение несёт:

| Поле | Значение |
| --- | --- |
| `name` | Собственное имя, чтобы компонент, которому передали только запись, всё равно мог поместить сообщение |
| `caption` | Заголовок действия, которое вывело сообщение; рисуется через [`<Caption value={m.caption}/>`](#caption) |
| `time` | Время появления сообщения в миллисекундах — то, которое стандартная панель печатает в строке с датой |
| `failed` | Является ли сообщение ошибкой — единственное различие между двумя сообщениями, которое делает панель, и то, по которому компонент их оформляет |

Сообщение — это разметка, поэтому проекция несёт только то, что стандартная панель пишет рядом с ней сама. Имя — собственное имя платформы: два сообщения могут нести один и тот же текст, заголовок и секунду, поэтому ничто в самом сообщении его не определяет.

`props.controller` делает то, что с окном сообщений может сделать только платформа: `togglePin()` переключает режим закрепления окна так же, как кнопка закрепления платформы. Закрепление — настройка среды отображения, общая с десктоп-клиентом, поэтому компонент не может выполнить её сам. Текущий режим ему тоже не передаётся, потому что его не знает и клиент: незакреплённое окно делает незакреплённым класс, который вычисляет сервер.

Сообщение, которое компонент никуда не поместил, всё равно выведено и всё равно есть в проекции: ничто его не удаляет — так же, как стандартная панель хранит все напечатанные сообщения. Поэтому компонент, показывающий только последнее сообщение или только ошибки, ничего не теряет: помещённое снова сообщение видно в том же виде. Ни очистки, ни закрытия сообщения нет ни в проекции, ни в контроллере, потому что их нет и в платформе.

Само окно остаётся окном платформы: компонент рисует внутри него, поэтому окно так же скрывается, выдвигается поверх формы и показывается при появлении сообщения, как и раньше.

Компонент рисует только десктопный веб-клиент. Десктоп-клиент оставляет свою стандартную панель сообщений, а на мобильный веб-клиент, в раскладке которого окна сообщений нет вовсе, это не влияет.

### Отрисовка изображения {#image}

Изображение, которое проецирует платформа, — свойство класса изображения, значок элемента навигатора или действия — рисуется компонентом `Image`:

```jsx
const { Image } = window.lsfusion;

<Image value={e.image} className="menu-icon"/>
<Image value={row.photo.value} className="avatar"/>
```

Проецируемое значение — это либо адрес, либо готовый элемент, поскольку у шрифтового значка адреса нет вовсе, и `Image` рисует то, что ему передали. Представлению, которому нужен сам адрес — например, для фона в CSS, — он по-прежнему доступен в значении. `Image` существует для того, чтобы разметку платформы не приходилось вставлять руками. Отсутствующее изображение не рисуется.

### Отрисовка заголовка {#caption}

Заголовок, который проецирует платформа, — заголовок формы, элемента навигатора или сообщения — рисуется компонентом `Caption`:

```jsx
const { Caption } = window.lsfusion;

<Caption value={e.caption} className="tab-caption"/>
```

Заголовок — это либо обычный текст, либо разметка, построенная платформой, и `Caption` рисует то, что ему передали, по тому же правилу, по которому платформа рисует собственный заголовок: значение считается разметкой, если тег встречается в нём где угодно. Напечатанный как текст, такой заголовок показал бы собственную разметку, поэтому представление, которое печатает `{e.caption}` само, право только пока заголовок — обычный текст. Отсутствующий заголовок не рисуется.
