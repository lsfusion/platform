[Вычисляемое свойство](../paradigm/Properties.md#calculated), созданное [группировкой](../paradigm/Grouping_GROUP.md), если оно не материализовано, вычисляется внутри каждого запроса, который его читает, как подзапрос. Когда действию такое свойство нужно лишь для части объектов, а условие, которое эти объекты отбирает, подзапрос не ограничивает, группировка может вычисляться для всех объектов с применением отбора к её результату, поэтому время действия может расти с размером таблиц, а не с числом нужных ему объектов. Какие условия платформа переносит внутрь подзапроса, описано в [материализациях](../paradigm/Materializations.md). Перенесено ли условие, видно по тексту запроса в [логе `explain`](../paradigm/Journals_and_logs.md#logs): перенесённое появляется и внутри подзапроса группировки, а условие, которое не перенесено, остаётся только снаружи.

В примерах используются заказы и история цен SKU:

```lsf
CLASS Sku 'SKU';
CLASS Stock 'Склад';

CLASS Order 'Заказ';
date 'Дата' = DATA DATE (Order) INDEXED;
shipped 'Отгружен' = DATA BOOLEAN (Order);
invoiced 'Счёт выставлен' = DATA BOOLEAN (Order);

CLASS OrderDetail 'Строка заказа';
order 'Заказ' = DATA Order (OrderDetail) NONULL DELETE INDEXED;
sku 'SKU' = DATA Sku (OrderDetail);
quantity 'Количество' = DATA NUMERIC[16,3] (OrderDetail);

CLASS PriceChange 'Изменение цены';
sku 'SKU' = DATA Sku (PriceChange);
date 'Действует с' = DATA DATE (PriceChange);
price 'Цена' = DATA NUMERIC[16,4] (PriceChange);
INDEX sku(PriceChange c), date(c), c;

// цена SKU на дату
price 'Цена' (Sku s, DATE d) = GROUP LAST price(PriceChange c) ORDER date(c), c WHERE date(c) <= d BY sku(c);
// сумма заказа по ценам на его дату
sum 'Сумма' (Order o) = GROUP SUM quantity(OrderDetail d) * price(sku(d), date(order(d))) BY order(d);
```

## Пример 1 {#example-1}

### Условие

Нужно действие, которое отмечает заказы, по которым пора выставить счёт: отгруженные заказы с датой не позже заданной, по которым счёт ещё не выставлен и сумма которых положительна. Почти по всем прежним заказам счета уже выставлены, поэтому отмечается немного заказов.

Отбор можно записать одним присваиванием:

```lsf
toInvoice 'К выставлению счёта' = DATA LOCAL BOOLEAN (Order);

selectToInvoice 'Отобрать заказы для счетов' (DATE to)  {
    toInvoice(Order o) <- NULL;
    toInvoice(Order o) <- TRUE WHERE date(o) <= to AND shipped(o) AND NOT invoiced(o) AND sum(o) > 0;
}
```

Ни дату, ограниченную только с одной стороны, ни отсутствие признака `invoiced[Order]` платформа не считает ограничивающими подзапрос свойства `sum[Order]`. Тогда суммы могут вычисляться для всех заказов, с поиском цены для каждой строки за всю историю, а условия по заказу — применяться к результату.

### Решение

```lsf
selectToInvoiceInSteps 'Отобрать заказы для счетов' (DATE to)  {
    toInvoice(Order o) <- NULL;

    // заказы, отобранные по их собственным хранимым свойствам
    LOCAL candidate = BOOLEAN (Order);
    candidate(Order o) <- TRUE WHERE date(o) <= to AND shipped(o) AND NOT invoiced(o);

    // сумма нужна только для них
    toInvoice(Order o) <- TRUE WHERE candidate(o) AND sum(o) > 0;
}
```

Присваивание свойству `candidate[Order]` читает только хранимые свойства заказа, поэтому СУБД отбирает кандидатов сразу по всем его условиям. Последнее присваивание читает `sum[Order]` для заказов, записанных в это [локальное свойство](../paradigm/Data_properties_DATA.md#local). Платформа знает, сколько объектов в таком свойстве, и ограничивает ими подзапрос, когда оценивает это как более дешёвое, — как в этом примере, где кандидатов мало среди множества заказов.

Условие стоит выносить в такое присваивание, когда платформа не считает его ограничивающим, как не считает здесь дату с одной границей и отсутствие признака. Равенство хранимого свойства заданному значению и диапазон между двумя заданными значениями по индексированному свойству класса даты или времени ограничивающими считаются, поэтому могут ограничить подзапрос сами: в действии, которое принимает обе границы периода, `(DATE from, DATE to)`, единственное присваивание с `date(o) >= from AND date(o) <= to` вместо `date(o) <= to` может вычислять суммы только заказов этого периода.

## Пример 2

### Условие

Аналогично [**Примеру 1**](#example-1), но для каждого отмеченного заказа действию нужна ещё и его сумма по текущим ценам.

```lsf
currentSum 'Сумма по текущим ценам' (Order o) = GROUP SUM quantity(OrderDetail d) * price(sku(d), currentDate()) BY order(d);

invoiceCurrentSum 'Сумма по текущим ценам' = DATA LOCAL NUMERIC[18,4] (Order);
```

### Решение

```lsf
fillCurrentSums 'Заполнить суммы по текущим ценам' (DATE to)  {
    selectToInvoiceInSteps(to);

    invoiceCurrentSum(Order o) <- NULL;
    invoiceCurrentSum(Order o) <- NUMERIC[18,4](currentSum(o)) WHERE toInvoice(o);
}
```

Условием второго присваивания служат отмеченные заказы, поэтому вторая группировка может ограничиваться ими так же. Один раз заполненное локальное свойство служит каждому дорогому свойству, которое нужно для тех же объектов, поэтому условия их отбора не повторяются в каждом присваивании.

## Пример 3

### Условие

Действие, которое готовит ценники склада, прочитало остаток каждого SKU на складе в локальное свойство. Нужны цены на заданную дату для тех SKU, которые есть в наличии.

```lsf
tagBalance 'Остаток' = DATA LOCAL NUMERIC[16,3] (Sku);
tagPrice 'Цена' = DATA LOCAL NUMERIC[16,4] (Sku);
```

### Решение

```lsf
fillTagPrices 'Заполнить цены ценников' (DATE d)  {
    tagPrice(Sku s) <- NULL;

    // SKU в наличии записываются в отдельное локальное свойство
    LOCAL inStock = BOOLEAN (Sku);
    inStock(Sku s) <- TRUE WHERE tagBalance(s) > 0;

    tagPrice(Sku s) <- price(s, d) WHERE inStock(s);
}
```

Сравнение остатка с нулём — диапазон с одной границей, поэтому в условии `WHERE tagBalance(s) > 0` ограничивающим считается только наличие значения в `tagBalance[Sku]`, а не само сравнение. Так как в `tagBalance[Sku]` записаны и SKU с нулевым остатком, запрос, читающий цены по этому условию, может сгруппировать всю историю цен и только потом проверить остаток. Перенесённое в присваивание, которое заполняет ещё одно локальное свойство, сравнение оставляет в этом свойстве только SKU в наличии.

Важно и число объектов: платформа ограничивает подзапрос локальным свойством, когда оценивает ограниченный подзапрос как более дешёвый, а в оценке участвует число объектов, записанных в локальное свойство. Поэтому в локальное свойство, которое ограничивает дорогую группировку, следует записывать только те объекты, для которых эта группировка нужна.

## Пример 4

### Условие

Нужна стоимость запасов каждого склада на каждую из выбранных дат. Остаток на дату вычисляется по движениям SKU.

```lsf
CLASS Ledger 'Движение';
sku 'SKU' = DATA Sku (Ledger);
stock 'Склад' = DATA Stock (Ledger);
date 'Дата' = DATA DATE (Ledger);
quantity 'Количество' = DATA NUMERIC[16,3] (Ledger);

balance 'Остаток на дату' (Sku s, Stock st, DATE d) = GROUP SUM quantity(Ledger l) IF date(l) <= d BY sku(l), stock(l);
value 'Стоимость на дату' (Stock st, DATE d) = GROUP SUM balance(Sku s, st, d) * price(s, d);

selected 'Выбрана' = DATA LOCAL BOOLEAN (DATE);
stockValue 'Стоимость' = DATA LOCAL NUMERIC[20,4] (Stock, DATE);
```

### Решение

```lsf
fillStockValues 'Заполнить стоимость' ()  {
    stockValue(Stock st, DATE d) <- NULL;

    FOR selected(DATE d) NOINLINE DO
        stockValue(Stock st, d) <- NUMERIC[20,4](value(st, d)) WHERE st IS Stock;
}
```

В одном присваивании — `stockValue(Stock st, DATE d) <- NUMERIC[20,4](value(st, d)) WHERE selected(d) AND st IS Stock;` — выбранные даты читаются из свойства `selected[DATE]` внутри запроса. Каждое движение соединяется со всеми выбранными датами не раньше его собственной, и данные всех дат группируются этим запросом, поэтому объём его промежуточных данных растёт с числом дат, и СУБД может записывать эти данные во временные файлы. Цикл выполняет по запросу на каждую дату, передавая дату значением, и каждый запрос обрабатывает данные одной даты. Общее время двух вариантов может быть близким: цикл ограничивает объём данных, которые обрабатывает один запрос, поэтому выбирать его стоит, когда единственное присваивание упирается в этот объём, а не во время.

Опция `NOINLINE` здесь нужна: без неё платформа может выполнить цикл, тело которого — присваивание, как то же единственное присваивание (см. [How-to: FOR](How-to_FOR.md), где в остальных случаях предпочтительно присваивание сразу для всех объектов).

## Пример 5

### Условие

Нужно действие, которое отмечает SKU, у которых есть изменение цены с датой позже заданной.

Условие можно записать как сравнение двух группировок — последнего изменения цены SKU и последнего её изменения не позже даты:

```lsf
lastChange 'Последнее изменение цены' (Sku s) = GROUP LAST PriceChange c ORDER date(c), c WHERE date(c) BY sku(c);
lastChange 'Последнее изменение цены на дату' (Sku s, DATE d) = GROUP LAST PriceChange c ORDER date(c), c WHERE date(c) <= d BY sku(c);

repriced 'Переоценён' = DATA LOCAL BOOLEAN (Sku);

selectRepriced 'Отобрать переоценённые SKU' (DATE d)  {
    repriced(Sku s) <- NULL;
    repriced(Sku s) <- TRUE WHERE d AND lastChange(s) AND NOT lastChange(s, d) = lastChange(s);
}
```

Тогда обе группировки вычисляются для всех SKU, прежде чем их можно сравнить.

### Решение

```lsf
lastChangeDate 'Дата последнего изменения цены' (Sku s) = GROUP MAX date(PriceChange c) BY sku(c) MATERIALIZED INDEXED;

selectRepricedByDate 'Отобрать переоценённые SKU' (DATE d)  {
    repriced(Sku s) <- NULL;
    repriced(Sku s) <- TRUE WHERE lastChangeDate(s) > d;
}
```

Условие, которое отбирает объекты, записано по материализованному свойству. В сессии, не изменившей историю цен, его значения читаются как хранимые, и при [индексе](../paradigm/Indexes.md) по нему СУБД может найти SKU по дате, не читая историю цен. То же верно, когда другая группировка агрегирует внутри себя данные объектов, отобранных таким условием, — например, суммирует строки заказов этих SKU: по материализованному свойству СУБД может найти их сначала, а сравнение не материализованных группировок проверяется только после того, как они вычислены. Как условие, которое отбирает объекты для группировки снаружи, оно остаётся диапазоном с одной границей — таким условием, какое в [**Примере 1**](#example-1) сначала записывается в локальное свойство.
